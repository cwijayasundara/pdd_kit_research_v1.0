# Fair first trial of PDD Kit (Proof-Driven Development)

Scope note for the report writer. This note is about **Microsoft Research and GitHub Next’s Proof-Driven Development Kit** (formal Verus proofs of agent-written Rust), not the unrelated open-source **Product-Driven Development** toolkit at [pdd-kit.dev](https://pdd-kit.dev/) (`npx pdd-toolkit`, Markdown product models, no prover). A third “PDD” ([promptdriven/pdd](https://github.com/promptdriven/pdd)) is prompt-driven development. Installing either of those would not test the pet-store claim. Sources below are primary unless marked **secondary**. Date of this research: 2026-11-07. No public Pet Store repository, PDD Kit issue tracker, or PDD Kit install document was found.

The published verification claim is **not** “a full-stack web app was proved.” It is: one security-sensitive slice (login) of a ~5,000-line Rust app was given a human-approved Verus spec; an agent wrote the code and the proof; Verus/Z3 checked that code against that spec for every input the spec talks about; six trusted pieces were accepted by a person and tested; the real handler was rewired through the proved function. Inventory, promotions, orders, checkout, and the Leptos UI are the host app, not the verified surface.

## What is the smallest app that still exercises the pet-store verification claim, and what is decoration?

### Takeaway
The smallest fair target is a Rust HTTP login (or permission) slice on the real request path, with an if-and-only-if security property, at least the password check and the account lookup left outside the proof, a spec approved before proof bodies exist, a per-clause vacuity check, and a deterministic Verus run. The pet storefront, catalog, cart, and checkout are not part of the published proof.

### Cited Findings
- Pet Store is a full-stack app written entirely in Rust: Axum and SQLite backend (inventory, promotions, orders, checkout) and a Leptos storefront compiled to WebAssembly, “about 5,000 lines” in all. The write-ups then “focus on formally verifying the login logic.” The same process is described as usable for the rest “one piece at a time,” which is a recommendation, not a result that the rest was proved. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, 2026-11-05](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The developer request that produced the demo was two sentences aimed at an existing file: “Verify the login logic in `backend/src/handlers/auth.rs`,” with (1) a token only with the right password and (2) admin tokens only for admin accounts. The request was kept rough on purpose. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The spec header says the flow was taken from `backend/src/handlers/auth.rs:82-127` at commit `8b8b70f`. No repository URL for that commit was published on either primary page. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- What was actually proved: bodies of `login_flow`, `login_core`, `lookup_target`, `decide_login`, and `issue_token` meet their contracts for every input. Login picks the table, compares the password to the hash of the account it names, issues a token with that account’s id and the role from that table, and refuses the other cases with today’s 400, 401, or 500 and no token. — [Microsoft Research blog, “What the proof does and doesn’t say”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The two-sentence request became eight `ensures` clauses on async `login_flow`. Four of those eight were not asked for; they pin today’s refusals so the storefront and existing API tests keep working (400 when neither email nor username is sent, 401 unknown account, 401 wrong password, 500 unreadable hash). — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 12](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Default scope was narrower than the published proof. The first draft proved only the decision (pick the table, gate on the password) and left the handler trusted and tested. The developers chose a wider async spec so the glue (await lookups, sign the token) is proved. That choice “moved almost everything into the proof” and left the Axum handler as unpack-and-await. The verified logic is wired into the production handler, “not a copy of it.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 6](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Six pieces stay trusted, each with an assumed contract and a planned test: `Customer::find_by_email`, `Admin::find_by_username`, `check_password` over `bcrypt::verify`, `generate_token` (JWT), `expiry_from_now` (clock, expiry exactly 86,400 seconds later), `database_error`, plus the handler shell that unpacks the request unchanged. Authors say the guarantees are only as strong as those six, and two carry most of the weight: `check_password` for every password promise, and the two lookups for every promise about which account a token names. Tests support them; nothing proves them. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Explicitly outside the proof, even for this slice: code the verifier cannot see (bcrypt, sqlx, jsonwebtoken); facts about the outside world (current SQLite rows, clock reading); whether and how fast login finishes (“No promise the future completes”); anything a person must judge (whether an error message helps, whether a screen makes sense); whatever nobody wrote down; how other endpoints read the role; rate or timing of attempts; a panic if the clock is out of range. UI and third-party crypto are named as empirical, via unit and end-to-end tests, terminal automation, browser agents, and computer-use agents. A passing test is labeled evidence, not proof. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 7](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Authors’ own starting rule: begin where a bug costs the most (login, payments, or permissions) and verify the rest one piece at a time. PDD Kit “only verifies Rust today.” Other languages can be ported to Rust and checked against the same spec, or a non-Rust project can call verified Rust through bindings. That is a porting story, not a verifier for arbitrary apps. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Stage on the project page is “Research Prototype,” published Nov 2026. It runs inside Chopin. The Oct 21, 2026 launch post called it a research preview and said it “works on Rust today.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [GitHub Next on X, 2026-10-21](https://x.com/GitHubNext/status/2112936525457740139)
- **Secondary.** A Japanese write-up of the same Nov pages repeats that only login was specified, that the spec ended as eight conditions, and that the kit is a limited research preview for Rust. It does not add a verified feature beyond login. — [gihyo.jp, 2026-11-05](https://gihyo.jp/article/2026/11/pdd-kit)

### Inferences
- Essential to the **same claim** as the demo: (1) an existing or at least production-path Rust handler, not a side file; (2) a decision core small enough for Verus (`lookup_target` / `decide_login` style) plus the async glue if the claim is “end to end,” which is what they chose over the recommended narrower default; (3) at least one real external the proof must axiomatize (password check and a lookup are the ones the authors say carry the weight); (4) a property that is easy to under-specify in one direction (token implies right password, vs right password implies token); (5) human approval of the spec and of each trusted contract before bodies are filled in; (6) a checker that is Verus/Z3, not the model; (7) a vacuity check so a green proof is not a weak spec; (8) tests only for the trusted ring, labeled as tests.
- Demo decoration relative to that claim: pet catalog, promotions, orders, checkout, Leptos/WASM UI, ticket-desk illustrations, the comprehension quiz as a teaching device, multiplayer presence, and the round number “5,000 lines.” Those show that the slice sits in a realistic app. They are not what was proved. A trial that rebuilds the storefront and calls the result “the same verification” has changed the claim.
- The smallest app that still matches the claim is therefore on the order of one Axum auth handler plus a SQLite (or equally opaque) user lookup and a bcrypt (or equally opaque) password check and a token signer: a few hundred lines of host code, not a store. Dropping the lookup and the password library turns it into a pure-function proof, which Verus can do without PDD Kit and which does not exercise the trusted-computing-base story the authors say is the weak link. Dropping the production-path rewire (proving a copy) misses the integration claim.
- The trial can speak for this class only: **functional correctness of a specified Rust function (including an async one) for every input, under assumed contracts for libraries and the outside world, on a web backend’s real path.** It cannot speak for “a web app was verified,” for UI correctness, for liveness, or for non-Rust systems.

### Gaps
- No public Pet Store tree was found, so line counts beyond “about 5,000,” the handler span `auth.rs:82-127`, and the 368-line spec file (next section) cannot be re-measured.
- Authors say the same process can cover payments or permissions and, eventually, functional correctness of the whole app. They do not show a second proved slice. Whether checkout (money, inventory decrement, idempotency) is in the same difficulty class as login is unknown.
- Whether a greenfield handler written entirely by the agent, rather than a slice extracted from existing `auth.rs`, was ever run is not stated. The demo is “integrating with existing codebases.”

## What counts as success versus a false proof, and what do the authors say to review?

### Takeaway
Success is a Verus-accepted proof of a spec a person approved, that rules out a planted bug per clause, with every trusted assumption named and tested, on the production path. A green check is a false proof if the spec is one-directional, vacuous, copied from the code, or silent about the wiring that matters, or if “verified” is used for the UI, the database, bcrypt, or termination.

### Cited Findings
- Authors’ name for the main failure mode is **vibe verification**: a model that writes its own spec, or is tuned to produce proofs, finds weak invariants that verify but rule out almost nothing. “A green checkmark on the wrong spec is worse than no checkmark.” The guard is a mutation check: `pdd-prove` plants one bug per `ensures` clause in a scratch copy, and Verus must reject each mutant on the clause it targets. A mutant that survives means the clause constrains nothing and comes back as a gap. Examples they give of planted bugs: refusing everyone, and checking the username before the email. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, FAQ and Step 6](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The first decision card is the worked example of a spec that is true and still useless. “You only get a token with the right password” is `token ⇒ right password`. A login that refuses everyone satisfies it. The converse (“the right password always gets a token”) is a separate clause. Together they are “if and only if.” An agent left alone “would have picked one without telling us.” The published success condition is both directions, with a 500 allowed only when lookup or signing actually fails, so “a login that answers 500 every time doesn’t meet the spec.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figures 2 and 5](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- **The two primary pages do not paste the same contract.** On the GitHub Next page, the success clause is `r is Ok || (Internal && (lookup_fails || signing_fails))`, and the 401 clauses similarly allow 500 only when `lookup_fails`. The Microsoft Research blog’s code block weakens those to `r is Ok || r matches Err(AppError::Internal(_))` and the same drop of `lookup_fails` on the 401 clauses. The prose on both pages says a 500 is only for a real lookup or signing failure. A trial that copies the blog’s code block would accept a login that returns 500 for a correct password even when lookup and signing succeeded. — [GitHub Next, `login_flow` contract](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, the `login_flow` listing](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- “A proof shows the code meets the spec, not that the spec is what you meant.” A wrong spec yields wrong verified code. Mitigation they describe, not a guarantee: `pdd-plan` asks questions before writing anything, flags ambiguity instead of guessing, two reviewer agents check that the spec matches the ask and does not promise more than a proof could show, and the mutation check catches vacuous clauses. “A wrong spec is still possible,” so a person still approves. Signing off on the plan “isn’t proof, and it doesn’t approve new trust.” — [Microsoft Research blog, FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, intent sign-off card](https://githubnext.com/projects/pdd-kit/)
- Agent-written tests are called out as a separate false assurance. “The agent writes the tests too. Those tests tend to pass for the code it wrote, not the code you meant.” Tests “only sample a handful of inputs.” Their counter-move for the trusted ring is to write Given/When/Then scenarios into the plan **before any test exists**, marked *planned* until a command’s result and commit are recorded. After a proof exists they **prune** example-based tests of what is already proved (the password gate) and keep tests of the trusted boundary. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The proof is not checked by a model. “The proof is Rust code annotated with Verus constructs, checked mechanically by Verus using the Z3 solver.” “The check is deterministic, with no model involved. Models write the spec, code, and proof, but only a deterministic Verus run decides whether it passed.” An LLM verifier is still in the loop, but only to look for requirements with no proof and no passing check. Gaps go back to the coding agent. A contradiction in the spec comes back as a human decision. If an async construct cannot be expressed in the pinned Verus, the task stops and asks rather than switching to a non-async helper or weakening a contract. — [Microsoft Research blog, FAQ and Step 6](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, build-plan task text](https://githubnext.com/projects/pdd-kit/)
- “Fully verified” is “easy to oversell.” Their own partition for login is three layers. **Proved:** the five function bodies above. **Trusted and tested:** lookups, bcrypt wrapper, clock, signing, database error string, request unpacking. **Assumed, not tested by the app’s tests:** the Verus toolchain, the Rust compiler, Z3, and Verus’s standard library `vstd`. — [Microsoft Research blog, “What the proof does and doesn’t say”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- A wiring property they say tests rarely catch: the same account `a` must appear in the password check and in the token claims. Checking Bob’s password and signing Alice’s id satisfies weaker per-step tests and fails that clause. Role is not a field of the request. Email, if sent, selects the customer table even when a username is also sent; the admin password on that request must not yield an admin token (their quiz answer is 401). — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 11](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Async contracts do not cover non-termination. `requires` is checked when the future is created; `ensures` describes the value only if the future finishes. A hung query breaks no clause. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 14](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Comparison table they publish: Spec-Driven Development enforces nothing; TDD checks a sample of inputs, “often written to match what was built”; “agent checks its own work” is the same model that wrote the code; Proof-Driven Development is Verus checking that code satisfies the spec you approved. They still use tests where a proof cannot reach. — [Microsoft Research blog, FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The at-a-glance line “Verus hardened the code and uncovered existing bugs” appears on the Microsoft Research blog and is **not** repeated as a list of defects on the GitHub Next page. The body of the blog never names those bugs. The bugs that are specified are mutants planted in a scratch copy to test the spec. — [Microsoft Research blog, at a glance](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- **Secondary, and partly stale relative to the Nov write-ups.** An Oct 22, 2026 commentary lists three limits (Rust only; only what a spec can express; research preview) and treats the vendor line about shipping without line-by-line review as “not an audited result.” It also says proof synthesis underneath is AutoVerus and VeruSAGE, “benchmarked against 150 and 849 verification tasks.” Those benchmark counts were **not** checked against the Microsoft repository for this note. The article’s sample `check_attempt` spec is the author’s illustration, not Pet Store. — [Piekwerk, DEV, 2026-10-22](https://dev.to/piekwerk/githubs-pdd-kit-proves-agent-written-rust-correct-5-steps-and-3-limits-l7l)

### Inferences
- A trial “passes” only if all of the following are true and recorded: the person can point at each clause and say which English sentence it is; Verus rejects a hand-planted bug aimed at each clause (not only the kit’s own mutator, if the kit is unavailable); the trusted list is explicit; the handler that serves the route calls the proved function; the proof command is a local Verus/Z3 invocation that a second machine can re-run on the committed files without calling a model.
- These are false proofs even if Verus says yes: type-checking or `cargo check` alone; a spec written by reading the implementation and restating it (`ensures r == <whatever the code returns>`); only the “only if” half of a security property; tests the agent wrote after the code, including tests of the proved core that were not in the plan; a UI walkthrough by a computer-use agent; a proof of a pure helper while the route handler is unproved and untested; calling the app verified because login’s spec passed; trusting the blog’s weaker `Internal(_)` paste over the GitHub Next clause that ties 500 to `lookup_fails || signing_fails`.
- “Uncovered existing bugs” should not be a success metric for the trial. The primary detailed text does not identify any pre-existing defect. The reproducible demonstration of bug-finding is the mutation check.

### Gaps
- No independent party is cited by the authors as having re-run the Pet Store proof. The DEV piece is a commentary on the announcement, written before the Nov long-form pages, and it links a news aggregator rather than a repo.
- No author statement was found on whether the human must re-read proof annotations (`assert`, loop invariants, `decreases`) or may ignore them entirely. They do say nobody needs to read the proof because Verus checks every step, and that the spec is what people review. They do not discuss proof-structure attacks beyond vacuous specs and the assumed toolchain (Verus, rustc, Z3, vstd).
- How strong the two “reviewer agents” are (model, disagreement rate, whether they can be skipped) is not stated.

## How much human effort do the authors still require?

### Takeaway
The human still writes or approves the intent, the formal spec, and each trusted assumption, and reads a pull-request receipt rather than the generated proof. The only size signal for that work is the login artifact itself (eight clauses, a 368-line spec file with empty bodies, six trust sign-offs, seven tasks). Hours, and lines of proof versus lines of code, are not reported.

### Cited Findings
- “You don’t need a formal methods background.” The login spec “is short enough to learn to read in a few minutes.” Every clause has a plain-English comment. Developers “review the natural-language plan, the formal spec, and the trusted components.” On Pet Store “this approach reduced reliance on exhaustive line-by-line review of the generated code.” The developer “reviewed the intent and never read the generated code line-by-line.” — [Microsoft Research blog, FAQ and at a glance](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- The spec file they walk through is `verified/src/login.rs`, “368 lines,” and at spec-approval time the five proved functions have **no bodies** (`unimplemented!()`). “The contracts come first, the team approves them, and only then does the proof stage write code.” The file “compiles as a module of the real backend crate,” naming real `Customer`, `Admin`, `Config`, and `AppError` types. — [GitHub Next, “An overview of login.rs”](https://githubnext.com/projects/pdd-kit/)
- Build plan for that spec is seven tasks: make `login.rs` build under Verus inside the backend crate; prove `lookup_target`, `decide_login`, and `login_core`; prove `issue_token`; prove `login_flow` end to end and rewire the handler; test the trusted wrappers; end-to-end login tests through the handler; signing-failure and signing-count tests. — [GitHub Next, build-plan figure](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 16](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Trust review is per piece, not one blanket accept. Login has six sign-offs. Each card shows the clauses Verus will assume, what the person is accepting, and which promise fails if the assumption is wrong. There is also a comprehension quiz in the demo (“Which window decides the role?”). — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- “Proofs still take real effort, mostly in producing the proof itself, and a clear spec is what keeps that effort down.” They contrast this with the old cost: specialists, unfamiliar languages, “proofs many times larger than the code,” and “years.” They do **not** publish a proof-to-code ratio, a person-hour figure, or a token figure for Pet Store. The diagram of where human time goes is captioned “illustrative, not measured.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, “Why Rust” / “What to Expect”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Solver time, which is not human time: “usually seconds for a small module, up to minutes for a larger codebase.” The check runs “wherever your Rust builds”; `pdd-prove` runs it while proving; `pdd-ship` adds it to the build and CI so a broken proof fails the build. — [Microsoft Research blog, FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Historical proofs being “many times larger than the code” is the pre-agent baseline they say has changed, not a measurement of `login.rs` after the proof annotations were filled in. The 368-line figure is the contract file before bodies. — [GitHub Next, “Why Proof, and Why Now”](https://githubnext.com/projects/pdd-kit/); [GitHub Next, login.rs overview](https://githubnext.com/projects/pdd-kit/)

### Inferences
- For a login-sized slice, the review surface the authors expect a person to actually read is: the intent artifact, about eight commented `ensures` clauses, six trust cards, and a receipt. That is the only scale for which they claim “a few minutes” of spec reading. It does not transfer to “the whole 5,000-line app.”
- Do not put a person-hour estimate in the plan. The sources do not support one. “Real effort, mostly in producing the proof” means the agent/prover loop, and they give no duration for that loop on Pet Store.

### Gaps
- Lines of proof annotation versus lines of executable code after `pdd-prove` finishes: unknown. The 368-line file explicitly excludes those bodies.
- How many decision cards were answered, how many quiz items exist, and whether a second person must approve: unknown. The workflow is described as a team in Chopin, but the published login session reads as one developer plus the tool.
- Wall-clock time of the seven-task prove loop: unknown. Only the later Verus re-check is bounded (“seconds” to “minutes”).

## What toolchain risk does a solo trial on macOS carry?

### Takeaway
As of 2026-11-07 the proof checker (Verus) installs from binaries, with a macOS Gatekeeper step, but the published prebuilt OS list does not include a current Apple Silicon macOS, and PDD Kit itself has no public installer. The Verus check is reproducible without the model; regenerating the proof with Claude Code, Codex, or Grok Build is not the published pipeline and is not claimed to be repeatable.

### Cited Findings
- PDD Kit “is a research prototype” and “runs inside Chopin.” The Nov 2026 project page does not link a repository, a release, an application form, or an install command. The Oct 21, 2026 announcement says “now in research preview.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [GitHub Next on X, 2026-10-21](https://x.com/GitHubNext/status/2112936525457740139); [GitHub on X, 2026-10-21](https://x.com/github/status/2112938664959562081)
- Chopin, the host, was open-sourced at [github.com/githubnext/chopin](https://github.com/githubnext/chopin). Its own project page, published Sep 2026, says: “Right now, Chopin is a very small, early research prototype. … We don’t recommend you attempt to use it today. But within a month or so, we will have ironed out enough creases to seriously entertain some alpha users.” It has an MCP server “which lets you use any agent with Chopin” for planning, then “move back into your agent of choice for implementation.” That sentence is about Chopin plans, not about the later PDD prove loop. — [GitHub Next, Chopin](https://githubnext.com/projects/chopin/)
- The login build task says “Verus is installed at a pinned revision with async fn support.” A specific commit version of Verus is installed from source, not from the weekly binary, per Verus’s own install note: “if you’re looking for a specific commit version, you’ll need to install from source.” — [GitHub Next, build-plan figure](https://githubnext.com/projects/pdd-kit/); [Verus INSTALL.md](https://github.com/verus-lang/verus/blob/main/INSTALL.md)
- Verus first-tier prebuilt artifacts, from the live `INSTALL.md` on main: MacOS 14 (arm), MacOS 15 (x86_64), Windows 2022 (x86_64), Ubuntu 24.04 (x86_64). “The general rule of thumb is that we lag one version behind the latest offered on Github.” Anything else “you may have to build `verus` from source.” macOS binaries are quarantined by Gatekeeper; the documented fix is `bash macos_allow_gatekeeper.sh`. `./verus` then tells you which `rustup` toolchain to install. The example error text in that file still mentions toolchain `1.86.0` and a Linux target triple; the file says the binary prints the real requirement. Z3 ships inside the binary release. Source builds use `./tools/get-z3.sh` and a pinned Z3. — [Verus INSTALL.md](https://github.com/verus-lang/verus/blob/main/INSTALL.md); [Verus BUILD.md](https://github.com/verus-lang/verus/blob/main/BUILD.md)
- No model name is given for the Pet Store run. “Models write the spec, code, and proof, but only a deterministic Verus run decides whether it passed.” `pdd-ship` puts that deterministic check in CI. Re-running CI does not require the original model **if the proof artifacts are what get committed**. Nothing is said about re-generating those artifacts with a different model. — [Microsoft Research blog, FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- **Secondary, predating the Nov pages.** On 2026-10-27 a writer reported searching the GitHub Next sitemap and finding no PDD Kit page, no application form, and no install docs, and treated access, eligibility, and cost as unknown. The project page now exists (Nov 2026). The install gap on that page is still there. — [techmoon.xyz, 2026-10-27](https://techmoon.xyz/pdd-kit-verus-rust-proof-driven-development/)
- **Name-collision trap, primary for the other project.** `pdd-kit.dev` installs with Node 22.12+ via `npx pdd-toolkit install` into Claude Code, Codex, Cursor, Gemini CLI, and Copilot. Its verify skill “reads the code (never runs it)” and compares it with a Markdown product model. ### Inferences
- A solo Mac trial has three separate risks that should not be collapsed. (1) **Access risk:** PDD Kit’s planner, trust cards, mutation loop, and `pdd-ship` may be unreachable because no public release was found; Chopin’s maintainers told people not to use Chopin yet, and that sentence has not been visibly withdrawn on the PDD page. (2) **Prover-install risk:** even with a pin, Apple Silicon on a macOS newer than 14 is outside the documented prebuilt matrix (arm builds are listed for MacOS 14 only), so a source build plus Gatekeeper plus a matching rustup toolchain is the likely path. (3) **Model risk:** Claude Code, Codex, and Grok Build can write Rust and even Verus text, but the authors’ reproducibility claim attaches to the Z3 check of committed artifacts, not to a second closed model producing the same proof. A trial that “re-runs the agent” and gets a different proof has not falsified the checker.
- If the kit cannot be obtained, a Verus-only reconstruction (person writes or approves the spec, any agent writes the proof, local `verus` is the gate) tests the **checker and the spec discipline**, not PDD Kit’s intent-formalization loop. The plan should name which of those two experiments is running.

## How should a harness user change workflow, and what does PDD Kit already enforce?

### Takeaway
PDD Kit, when its workflows actually run, already gates code on an approved Verus spec, per-assumption sign-off, a vacuity mutant per clause, and a CI failure if the proof breaks. A coding-agent harness still has to force spec-before-code and freeze the trusted tests, because the user’s current harness checks behaviour with tests, and PDD Kit is not available as a Claude Code or Codex skill.

### Cited Findings
- Fowler (Böckeler, 2 April 2026) defines a coding-agent user’s harness as guides (feedforward) plus sensors (feedback), each either computational (deterministic, CPU) or inferential (model-judged). The behaviour harness, as commonly practiced, is a functional spec plus an AI-generated test suite that is green and has coverage, sometimes mutation testing, plus manual testing. “This approach puts a lot of faith into the AI-generated tests, that’s not good enough yet.” “Correctness is outside any sensor’s remit if the human didn’t clearly specify what they wanted in the first place.” The human’s job is to direct attention where it matters, not to eliminate it. Mutation testing is given as an example of an expensive sensor that belongs after integration, not on every keystroke. — [Böckeler, “Harness engineering for coding agent users”](https://martinfowler.com/articles/harness-engineering.html)
- rig_v1 (README on `main`, status dated 2026-11-03; plugin version 0.7.0, last tag `v0.4.1`) is “a behavioural harness” for Claude Code. Work starts from `intent.md` with numbered behaviours. A person runs `/rig:approve`; “a model never approves.” Approval hashes `spec.md`, `plan.md`, and contract files and goes stale if they change. `/rig:build` is test-first: one failing test per behaviour, then the code. `red-proof` runs new tests on the base without the new code and requires them to fail. Sensors include lint, tests, mutation, layering, and a test-tamper check. `rig-check` in CI re-judges with the base branch’s checker. “Scripts decide; models only advise.” On small tasks measured 2026-10-31, rig plus Haiku did not pass more hidden tests than plain Haiku (3/3 in every arm) and cost about 3× ($0.087 vs $0.032) and about 3× the wall time (8.2 min vs 2.4 min). The README’s own advice: use rig when a trail is needed; for a solo, small, fast change, plain Claude Code is faster and cheaper. — [rig_v1 README](https://github.com/cwijayasundara/rig_v1)
- What the PDD Kit workflows enforce, in the authors’ description: `pdd-plan` asks questions before code and will not silently pick one reading of an ambiguous sentence; two reviewer agents comment on the spec; the person signs the plan and each trusted contract; bodies are written only after that sign-off; the prove loop refuses to weaken a contract when Verus cannot express a construct; one mutant per clause must fail; an LLM gap checker looks for requirements with neither a proof nor a passing test; `pdd-ship` fails CI when the proof breaks and drops tests that only re-check a proved property. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- What those workflows do **not** claim to enforce: that the approved spec is what the person meant (“a wrong spec is still possible”); that trusted tests are complete (“tests support them, but nothing proves them”); UI, termination, rate limits, or other endpoints’ use of the role; any language but Rust; use outside Chopin. — [Microsoft Research blog, FAQ and “What the proof does and doesn’t say”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- rig’s behaviour evidence is tests tied to numbered behaviours, not a proof of all inputs. Fowler’s behaviour-harness section says that pattern is the open problem. PDD Kit’s authors make the same criticism of agent-written tests and answer it with Verus for the specified slice only. — [rig_v1 README](https://github.com/cwijayasundara/rig_v1); [Böckeler](https://martinfowler.com/articles/harness-engineering.html); [Microsoft Research blog, FAQ table](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

### Inferences
- Labeled as inference, not as something either author wrote. For this user, PDD Kit is a **computational behaviour sensor** for one Rust slice, which is the hole Fowler names and which rig does not fill. rig already supplies the feedforward half Fowler asks for (intent, human approval, frozen contracts) and several computational sensors aimed at tests (red-proof, test-tamper, mutation). Those still apply to the **trusted** tests, because the agent writes them. They do not become redundant just because Verus is green on `decide_login`.
- Labeled as inference. The harness should enforce, and PDD Kit does not enforce from inside Claude Code, Codex, or Grok Build today: one spec file that is the contract (do not keep a prose `spec.md` and a Verus `ensures` block that can drift); approval recorded before any proof body exists; CI invokes `verus` on that file and fails closed; trusted Given/When/Then text is frozen before the test implementation, and a test-tamper check stops the agent “fixing” those tests; the route handler is in the diff that must call the proved function; the PR body lists proved / trusted / assumed / not promised, copied from the authors’ receipt, and a model cannot check that box alone.
- Labeled as inference. The harness should **not** re-implement decision cards, the quiz, or the two reviewer agents if the real `pdd-plan` is available. If it is not available, pretending a Claude skill is PDD Kit is a false trial. A thin harness around Verus is an honest smaller experiment and should be named as such.
- Labeled as inference. Do not point rig’s mutation sensor and PDD’s clause-mutator at the same claim without saying which is which. rig’s mutation (as described) scores tests. PDD’s mutation scores spec clauses. Fowler treats test mutation as a post-integration sensor. A login-sized Verus run is “seconds” for a small module, so it can sit further left than a full mutation suite, but that timing is the authors’ general FAQ answer, not a measurement on this Mac.

### Gaps
- No document maps PDD Kit workflows onto Claude Code hooks, Codex, or Grok Build. The Chopin MCP note is about editing plans with “any agent,” and it predates the PDD write-up.
- Whether `pdd-ship` emits a normal `cargo`/`verus` command a foreign CI can run, or only a Chopin-internal step, is not specified beyond “adds it to your build and CI.”

## What phases, entry, exit, and stop conditions follow from the documented limits?

### Takeaway
Four phases match the evidence: confirm what the kit actually is, re-establish the published login proof or an explicit substitute, cut to a new app with the same proof surface, then change one clause and show the old proof fails. Each phase has a documented reason to stop that is a limitation, not a lack of enthusiasm.

### Cited Findings
- **Orient.** The artifact to study is the login spec, not the store: five proved functions, six trusted sign-offs, eight clauses, proof versus test versus “not promised.” The kit is a research prototype inside Chopin, and Chopin’s page still says not to use Chopin yet and points at a public repo rather than a PDD Kit release. Verus itself is public, MIT-licensed, and installable apart from the kit. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [GitHub Next, Chopin](https://githubnext.com/projects/chopin/); [Verus INSTALL.md](https://github.com/verus-lang/verus/blob/main/INSTALL.md)
- **Reproduce.** The published build is seven tasks on a pinned Verus with async support, ending in a handler that only unpacks the request and awaits `login_flow`, plus tests for trusted wrappers. The loop’s own stop rule: if the pinned Verus cannot express an async construct, stop and ask; do not weaken the contract or drop to a sync helper. — [GitHub Next, build plan](https://githubnext.com/projects/pdd-kit/)
- **Shrink.** Authors say start at login, payments, or permissions, one piece at a time, and that the UI, third-party crypto, queries, clock, termination, and unwritten requirements are outside the proof. The interesting residue they tell the reader not to skip is the trusted ring, especially `check_password` and the lookups. — [GitHub Next, “What to Expect” and “Where Proof Stops”](https://githubnext.com/projects/pdd-kit/)
- **Change one requirement.** Contracts are modular: “Change the body of `decide_login` and only `decide_login` gets proved again,” because callers are proved against the callee’s contract. Changing the **spec** is different: approval hashes in a harness go stale when the spec changes (rig), and PDD returns spec contradictions to the human rather than letting the agent edit the goal. A one-clause change is the smallest re-verification the architecture supports. — [GitHub Next, on `login_flow` using only callee contracts](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Step 6](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [rig_v1 README, approval staleness](https://github.com/cwijayasundara/rig_v1)
- Solver re-check cost for a small module is “usually seconds,” which is the only timing basis for putting the proof in the inner loop. Proof **search** cost is unstated. — [Microsoft Research blog, FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

### Inferences
- These entry, exit, and stop lines are planning inferences built only from the findings above. They are not author-published trial phases.
- **Phase A — Orient.** Entry: the two primary pages and Verus `INSTALL.md` have been read, and the other `pdd-kit` has been ruled out. Exit: a one-page boundary note in the trial repo listing proved / trusted / assumed / not promised for login, in the authors’ three-way split, plus a written decision of “PDD Kit workflows” versus “Verus plus my harness” based on whether the kit can actually be started. Stop: no way to run either Verus or the kit on this Mac (prebuilt matrix miss and source build fails), or the only “PDD” that installs is the product-model npm package. Do not continue by verifying a Markdown model and calling it the proof.
- **Phase B — Reproduce the sample.** Entry: Phase A’s decision, a Rust toolchain, and either the real Pet Store at `8b8b70f` or a written statement that the sample is unavailable. Exit: `verus` accepts the eight-clause `login_flow` (the tighter GitHub Next form, not the blog’s weakened `Internal(_)` paste); each clause has a mutant that Verus rejects; the six trust tests run against real bcrypt and the real schema; the HTTP handler contains no decision logic. Stop: the only way to go green is to weaken a clause, drop `async`, or prove a copy that the route does not call. That is the authors’ own stop, and it means the sample was not reproduced.
- **Phase C — New app, same surface.** Entry: Phase B exit, or an explicit downgrade recorded in Phase A. The new app is one auth (or permission) route, not a store. Exit: same checklist as Phase B on code the person did not copy from the blog, including one ambiguity the person had to answer (both-ways or equivalent) **before** bodies existed. Stop: the property is about the screen, latency, rate limits, or “the app works”; or the proof closes only because lookup and password checking were stubbed in pure functions with no trusted boundary. That would no longer be the pet-store claim.
- **Phase D — One requirement change.** Entry: Phase C exit, with the spec hash or approval recorded. Change exactly one clause (for example, email-no-longer-wins, or expiry no longer 24 hours, or admin tokens additionally require a second factor that is in the spec). Exit: the previous proof fails on that clause; a new proof passes; the mutant for the new clause still fails; trusted tests that the change does not affect still pass; the person re-approved the spec. Stop: the agent makes the old proof pass by editing the clause, deleting the test, or marking the new requirement “not promised.” Also stop if the desired change is one the authors list as inexpressible (must finish, must be fast, UI quality). Record that as “out of class,” not as a failed proof.

### Gaps
- No author timeline, sample repo, or tutorial exercise exists to copy these phases from. They are a reading of the demo’s structure.
- Phase B may be impossible without private access. The notes do not establish that the Pet Store commit is public.

## What can this trial not answer, so the plan does not overclaim?

### Takeaway
A successful login-scale trial shows that this person can get a specified Rust auth slice proved and re-proved. It does not show that PDD Kit verifies web apps in general, that it scales past one module, that a team can work in it, or that non-web systems are in reach.

### Cited Findings
- Authors: “Pet Store’s login is one piece of one app.” They “want to find out how far this scales.” They “expect that trusted boundary to shrink significantly over time,” which is a hope, not a result. They would verify “the rest of a codebase one piece at a time,” starting at login, payments, or permissions. — [GitHub Next, “What to Expect”](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Rust only, because Verus is Rust. Other proof languages “could” be used the same way; that is not a claim that they have been. Non-Rust code is “ported” or called “through bindings.” — [Microsoft Research blog, FAQ “Is it Rust only?”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The host is a web app, but the unverified list includes the UI, termination, performance, rate of attempts, and “how other endpoints read the role.” So even inside this web app the proof does not compose across endpoints unless each one is specified. — [GitHub Next, “Where Proof Stops”](https://githubnext.com/projects/pdd-kit/)
- Team use is a Chopin feature (multiplayer plans, decision logs). Chopin is a research prototype whose authors said not to use it yet. No study of multi-person review time, disagreement, or audit trails on the Pet Store spec was published. The time diagram is “illustrative, not measured.” — [GitHub Next, Chopin](https://githubnext.com/projects/chopin/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- The assumed base of the proof includes Verus, rustc, Z3, and `vstd`. A trial does not audit those. — [Microsoft Research blog, “Assumed”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- rig’s own evaluation warning is relevant as positioning only: on the tasks they tried, the harness did not beat a bare model, and “a lift could show on a model that fails bare, on work that drifts across sessions, or on requirements the brief does not state; none is built yet.” PDD Kit offers no cross-session or multi-agent evaluation either. — [rig_v1 README](https://github.com/cwijayasundara/rig_v1)

### Inferences
- Claims the plan should refuse even after a green trial: “I can verify apps with PDD Kit”; “the store is verified”; “we can skip review”; “this will work for our non-Rust services”; “the team workflow is ready”; “proofs removed the trusted crypto and SQL”; “a different model will reproduce the proof.”
- The honest sentence after a successful Phase D: a specified Rust login (or permission) function, called by the real handler, met an approved spec for all inputs Verus considers, assuming bcrypt, the queries, the clock, the signer, the unpacking, and the prover toolchain, and a one-clause change forced a new proof.

### Gaps
- No scaling data (second module, whole Pet Store, proof time versus LOC, how the trusted set shrinks) exists in the sources.
- No team-use data.
- No non-web case study (CLI, batch, embedded, distributed) was published. Login’s async split (proved core, trusted I/O) might carry, but that is not shown.
- No security claim beyond the login spec. “Absence of login bugs” on the Microsoft blog is absence relative to the spec, and the headline’s “uncovered existing bugs” is not itemized.

## Recommendations for the report writer

These are recommendations, not findings.

- State the trial’s claim in one sentence before any phase: “A Rust auth handler on the production path meets an approved Verus spec for every input, with the password check and the account lookup explicitly unproved and tested.” Do not claim a verified pet store.
- Keep the app at login scale. Do not design inventory, checkout, or a Leptos UI. Those are decoration relative to the published proof.
- Prefer the GitHub Next text of the eight clauses over the Microsoft Research blog’s code block when they disagree, and show both the “only if” and the “if” directions. Treat a 500 that is not tied to a real lookup or signing failure as a spec bug.
- Make success a checklist: person-approved spec before bodies; Verus exit 0; one rejected mutant per clause; six-style trust list with tests written down first; handler is a shell; CI runs `verus` without a model; one later clause change breaks the old proof. Make the false-proof list equally explicit: types only, spec copied from the code, agent-written tests of the proved core, UI evidence, a proof that is not on the route, the npm product-model kit.
- Split Phase A’s fork in the plan. If PDD Kit cannot be started, the rest of the trial is “Verus plus the harness,” and the write-up must say that. Do not backfill with `pdd-kit.dev`.
- For the harness, add a computational proof sensor and keep rig’s human approval, red-proof, and test-tamper on the trusted tests only. Do not let two specs (prose behaviours and `ensures`) evolve separately. Do not spend the trial rebuilding Chopin’s multiplayer UI.
- Put the open questions (scale, team, non-web, non-Rust, trusted-base shrinkage, which model generated the proof) in a “this trial will not show” box so a green Phase D cannot be narrated as a general verifier.
