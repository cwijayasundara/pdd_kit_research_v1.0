## What user-facing features does the pet store implement?

### Takeaway
The only user flow specified from behavior, not from a slogan, is login: `POST /api/auth/login` for a customer (email) or an admin (username), returning a JWT or today’s HTTP error. The MSR post says the backend also “handles inventory, promotions, orders and checkout,” but neither write-up lists those screens, routes, or rules. A cart is never mentioned.

### Cited Findings
- Login request the authors actually gave the tool: “Verify the login logic in backend/src/handlers/auth.rs. Here are my requirements: 1. You only get a token with the right password. 2. Only admin accounts get admin tokens.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); identical on [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Endpoint and shape, from the spec and the interactive explorer: `POST /api/auth/login` with JSON fields `email`, `username`, and `password`. Example success body in the explorer: `{ "email": "ana@example.com", "password": "hunter2" }` returns “200 with token,” role `"customer"`, expiring 24 hours after the clock reading. Admin example: username `admin`, password `admin123`, role `"admin"`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Identity rule, written as `named_account`: if an email is sent, look up `customers` and the role is `"customer"`; otherwise if a username is sent, look up `admins` and the role is `"admin"`; otherwise none. Email wins when both are sent. The comprehension-check card states the concrete case: email `ana@example.com`, username `admin`, password `admin123` (the admin’s password) returns **401 and no token**, because the email window wins and `admin123` is not Ana’s password. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Outcomes the spec keeps so “the storefront and the existing API tests keep working”: 400 with today’s message when neither email nor username is sent; 401 for an unknown account; 401 for a wrong password; 500 and no token when bcrypt cannot read the stored hash; 500 when lookup or signing fails. Success is a token whose `sub` is that account’s id and whose `role` is the table’s role. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Two tables are named: customers looked up by exact email (`Customer::find_by_email`) and admins by username (`Admin::find_by_username`). There is no third “users” table in the spec. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Planned password tests name a seeded admin hash that “accepts admin123 and rejects Admin123,” so the admin password check is case-sensitive at least for that seed. Customer examples: `hunter2` against its own hash is `Ok(true)`; `hunter3` and the empty string are `Ok(false)`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Storefront exists (Leptos, compiled to WASM) and already had API tests before this verification pass. No page, route, or component name for the storefront is given. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- MSR, and only MSR, says the backend “handles inventory, promotions, orders and checkout.” GitHub Next does not list those features. Neither source lists a catalog, a cart, registration, logout, or an admin CRUD UI. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); contradicted by omission on [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Explicitly **not** part of the login proof, listed under “Not promised”: that login ever finishes, how fast it answers, rate of attempts, how other endpoints read the role, clock-range panics, and anything nobody wrote down. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

### Inferences
- For a smaller copy of the *verified* slice, implement two accounts tables, one login route, JWT claims `{sub, role, exp}`, and the 200/400/401/500 matrix above. Do not add a cart unless you are deliberately going beyond what was verified.
- “Inventory, promotions, orders and checkout” is an author claim about the unverified rest of the app, not a feature list you can imitate from source. Treat it as a one-sentence scope hint only.

### Gaps
- No schema, no other routes, no promotion or checkout rules, no UI inventory of pages. Cannot say whether checkout charges a card, decrements stock, or is a stub.
- No statement of whether customers can self-register, whether admins have any API beyond login, or how the Leptos app stores the token.
- “Existing API tests” are mentioned but not listed, except the planned trusted-boundary tests in the login plan.

## Tech stack

### Takeaway
Rust on both sides: Axum + sqlx + SQLite on the server, Leptos compiled to WebAssembly in the browser, JWT via jsonwebtoken, passwords via bcrypt, time via chrono. Package manager is Cargo (`cargo test -p backend`). HTTP JSON, not GraphQL. No versions are published.

### Cited Findings
- “full-stack web app written entirely in Rust. The backend uses Axum and SQLite… The storefront is a Leptos app compiled to WebAssembly.” — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); same stack without the word “entirely” on [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Database access in the spec is `sqlx::SqlitePool` and `sqlx::Error`. Lookups are async (`.await`). The pool is opaque to the proof (`ExPool`). — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Password check is `bcrypt::verify(password, hash).map_err(|e| e.to_string())` inside trusted `check_password`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Signing is described as jsonwebtoken, outside the proof: “bcrypt’s hashing, sqlx’s queries and jsonwebtoken’s signing live in other crates.” `generate_token` “signs exactly the claims it is given under the configured secret” (`config.jwt_secret`). — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Clock is chrono: “chrono's clock is outside the proof.” `expiry_from_now` ensures `r.exp as int == r.now as int + 86_400` and “panics if the time is out of range, as today's login does.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- HTTP layer is Axum. The handler uses “the axum extractor” to unpack the request; after verification, `login` “only unpacks the request and awaits `login_flow`.” Errors are an app enum: `AppError::BadRequest(m)`, `AppError::Unauthorized`, `AppError::Internal(_)`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- The only printed test command is `cargo test -p backend check_password`, so the backend is a Cargo package named `backend`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- API style for the verified route is JSON over HTTP POST, not a named IDL. No OpenAPI, TypeSpec, or GraphQL file is mentioned. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Verifier toolchain assumed by the proof: Verus, the Rust compiler, Z3, and Verus’s standard library vstd. “Verus is installed at a pinned revision with async fn support.” The pin is not named. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)

### Inferences
- A faithful small stack is a Cargo workspace, Tokio (required by Axum and sqlx async), sqlx with the SQLite feature, bcrypt, jsonwebtoken, chrono, and Leptos+WASM only if you need the storefront. The proof does not depend on Leptos.
- `86_400` seconds is 24 hours added to a Unix-style integer clock, not a parsed datetime string, in the spec they printed.

### Gaps
- No Rust edition, MSRV, Axum/Leptos/sqlx/bcrypt/jsonwebtoken/chrono versions, JWT algorithm (HS256 is typical but not stated), or whether the Leptos app is CSR, SSR, or hydrated.
- No `cargo verus` or `verus` binary invocation is printed. “Pinned revision” has no hash.
- Package manager for the frontend (if any Node/Trunk/cargo-leptos) is not stated. WASM is the compile target, not a second language.

## How are specs written?

### Takeaway
Specs are Verus contracts in Rust (`requires`/`ensures`, ghost `spec fn`s, `external_body` / `external_fn_specification`), file `verified/src/login.rs`, with a plain-English comment on every clause. They are not Lean, Dafny, TLA+, Alloy, TypeSpec, or OpenAPI. Tests for trusted pieces are Given/When/Then scenarios in the plan, later Cargo tests. The login spec is eight `ensures` clauses on async `login_flow`, plus smaller contracts on four helper functions.

### Cited Findings
- “The parts of your intent that can be formalized become a formal specification in Verus… The rest, which has to be taken on trust, becomes informal specs that it checks with tests.” Other tools are named only as contrasts: “Lean and Dafny, which prove code meets a spec, and TLA+, which checks the design.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- File layout they print, top to bottom: header (lines 1–8); Verus setup (10–17); external type specs (19–48); abstract views (50–65); words the contracts use (67–85); `named_account` (87–110); trusted lookups (112–134); trusted `check_password` (136–148); trusted clock (150–168); trusted signing and database errors (170–193); data the proved code passes (195–225); proved `login_flow` (227–252); `login_core` (254–277); `issue_token` (279–297); `lookup_target` (299–311); `decide_login` (313–336). The proved functions start as contracts; “Bodies of proved functions are written by the proof stage.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Abstract state is uninterpreted: `customer_on_file`, `admin_on_file`, `bcrypt_verdict`, `token_claims`, plus failure predicates `customer_lookup_fails`, `admin_lookup_fails`, `signing_fails`. `password_matches` is an open spec fn: `bcrypt_verdict(password, hash) == Some(true)`. These never run. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Representative properties, as printed for `verified/src/login.rs` on the GitHub Next page (preferred when the MSR blog shortens a clause):
  1. Token only for the named account, right password, and that id and role — `login_flow` ensures: `r matches Ok(t) ==> (named_account(email, username) matches Some(a) && password_matches(password@, a.password_hash) && token_claims(t@, config.jwt_secret@) matches Some(c) && c.sub@ == a.id && c.role@ == a.role)`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
  2. Both-ways success, with a narrow 500 escape — `(named_account(...) matches Some(a) && password_matches(...)) ==> (r is Ok || (r matches Err(AppError::Internal(_)) && (lookup_fails(email, username) || signing_fails(config.jwt_secret@))))`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
  3. Admin role only from the admins table with no email — `(r matches Ok(t) && token_claims(...) matches Some(c) && c.role@ == admin_role()) ==> (email is None && username matches Some(u) && admin_on_file(u@) is Some)`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
  4. Email wins, on `lookup_target` — `email matches Some(e) ==> r == Ok(LookupTarget::CustomerByEmail(e))`; neither identity `==> r == Err(LoginError::MissingIdentity)`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- The other four `login_flow` clauses (eight total): missing identity is `Err(AppError::BadRequest(m))` with `m@ == missing_identity_text()`; unknown account is 401 unless lookup fails with 500; wrong password (`bcrypt_verdict == Some(false)`) is 401 unless lookup fails with 500; unreadable hash (`bcrypt_verdict is None`) is `Err(AppError::Internal(_))`; an email login’s token has `c.role@ == customer_role()`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- `decide_login` additionally pins: no row `==> Unauthorized`; `r is Ok` only if a row exists and `password_matches`; right password on a found row `==> r is Ok`; `AdminByUsername` yields role text `"admin"`; `CustomerByEmail` yields `"customer"`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Trusted `check_password` (`#[verifier::external_body]`, lines 136–148): `r is Ok <==> bcrypt_verdict(password@, hash@) is Some` and `r matches Ok(b) ==> bcrypt_verdict(...) == Some(b)`. Trusted lookup `ex_customer_find_by_email`: `r matches Ok(found) ==> found == customer_on_file(email@)` and `r is Err <==> customer_lookup_fails(email@)`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- `login_flow` is `async fn`. The doc comment says “No promise the future completes.” `requires` is checked when the future is created; `ensures` applies only to `r` after `.await`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- `LoginError` separates the decision from HTTP: `MissingIdentity` (400), `Unauthorized` (401), `UnreadableHash(String)` (500), `Database(sqlx::Error)` (500). `issue_token` maps those to “today’s” status codes. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Human-facing twin of the spec is an “intent artifact” in the Chopin plan: decision cards, a rough-work section (flowchart, spec landscape, intent map), and English above every clause. Two reviewer agents check that the formal spec matches the intent and does not promise more than a proof could show. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Empirical specs are Given/When/Then in the plan’s Empirical verification section, marked *planned* until a run, then “the command’s result and the commit it ran against.” Example id: `§4.1.1 check_password_answers_with_bcrypts_verdict` and `§4.1.2 check_password_errors_only_on_unreadable_hash`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Disagreement on the printed contract: the MSR blog’s `login_flow` listing drops the `lookup_fails || signing_fails` conjunct. Its success clause ends `==> (r is Ok || r matches Err(AppError::Internal(_)))`, and the 401 clauses likewise allow any `Internal` without tying it to `lookup_fails`. MSR introduces that block with “doc comment trimmed,” and several signatures in that post are missing type arguments (`Result` with no parameters, `Seq` with no type). The GitHub Next page prints the stricter clauses and an explorer that matches them. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); contradicted in the stricter form by [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)

### Inferences
- Prefer the GitHub Next clause text if you reimplement. The MSR version would let a login return 500 on a correct password even when lookup and signing did not fail, which is a weaker spec than the project page.
- The spec is a contract-first file: approve `ensures`, then fill bodies. Copying only the function signatures without `ensures` is not the artifact they reviewed.

### Gaps
- The full 368-line file is not published as a raw file; only excerpts and a section map. `login_core` and `issue_token` bodies/clauses are summarized, not fully pasted.
- No separate `.vrs`, Lean, or property-test file. No count of `ensures` clauses beyond the eight on `login_flow` plus the partial helper clauses they pasted.
- Exact string of `missing_identity_text()`, `customer_role()`, and `admin_role()` is not pasted (roles are described as the text `"customer"` and `"admin"`).

## What verification commands are run, and what was the result?

### Takeaway
The published result is a partial proof: five functions proved against their contracts for every input, six (or seven, depending on the page) trusted dependencies only tested, toolchain assumed. They name one Cargo test filter and seven Chopin tasks. They do not publish a Verus command line, a pass/fail log, a bug count, a model name, or a Pet Store runtime.

### Cited Findings
- Workflows, by name: `pdd-plan` (questions, intent artifact, Verus spec), `pdd-prove` (code, proof, tests, mutation check, LLM gap review), `pdd-ship` (adds the Verus check to build and CI so a broken proof fails the build). The developer action that starts proving is clicking **Build plan** in Chopin, which runs “on a development machine.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Seven tasks, in order, from the Build tab screenshot description: (1) make `verified/src/login.rs` build under Verus inside the backend crate, without changing what any contract promises, and stop rather than weaken a contract if an async construct cannot be expressed; (2) prove `lookup_target`, `decide_login`, and `login_core`; (3) prove `issue_token`; (4) prove `login_flow` end to end and rewire `login` as its shell; (5) test the trusted wrappers’ contracts; (6) end-to-end login tests through the handler; (7) signing-failure and signing-count tests. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); same seven-task split on [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The only concrete shell command printed: `cargo test -p backend check_password`, “covering the check_password ensures clause,” status **planned** in the screenshot, not a recorded pass. Scenarios under that test: `hunter2` vs its hash returns `Ok(true)`; `hunter3` and `""` return `Ok(false)`; seeded admin hash accepts `admin123` and rejects `Admin123`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Loop inside each task: a coding agent writes implementation and proof; Verus checks them; an LLM verifier looks for requirements with no proof and no passing check; gaps go back to the agent; spec contradictions go back to the team as decisions. “If an async construct can’t be expressed in the pinned Verus, the task stops and asks rather than switching to a non-async helper or weakening a contract.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Spec soundness check: “plants one bug per `ensures` clause in a scratch copy” (examples: refusing everyone, or checking the username before the email) and Verus must reject each mutant on the targeted clause. A mutant that verifies is a gap. No count of mutants or failures is given. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- What they claim was proved: “The bodies of `login_flow`, `login_core`, `lookup_target`, `decide_login` and `issue_token` meet their contracts for every input. Login picks the right table, compares the request’s password against the stored hash of the account it names, issues a token with that account’s id and the role its table gives, and refuses everything else with today’s 400, 401 or 500 and no token.” — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- What they claim was not proved: lookups, `check_password`, clock, JWT signing, `database_error`, and request unpacking. “Tests against the real bcrypt, the real SQLite schema and the real router cover them.” Assumed without test or proof: Verus, rustc, Z3, vstd. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- “Verus hardened the code and uncovered existing bugs, proving the absence of login bugs with respect to the specification.” No bug list, no count. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The proof check “is deterministic, with no model involved. Models write the spec, code, and proof, but only a deterministic Verus run decides whether it passed.” Duration guidance is generic, not a Pet Store measurement: “usually seconds for a small module, up to minutes for a larger codebase.” — [MSR blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- CI behavior they describe, not a workflow file: `pdd-ship` runs Verus next to empirical tests; tests that only re-check a proved property (example-based tests of the password gate) are pruned; trusted-boundary tests stay. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Count of trust sign-offs disagrees. GitHub Next: “six sign-offs” / “six trusted pieces,” and the file header lists two lookups, `check_password`, `expiry_from_now`, `generate_token`, `database_error` (that is six). It also says request unpacking “stays outside,” while the proof-boundary figure puts “request unpacking” in the trusted ring. MSR’s “six pieces” bullet list is: two lookups, `check_password`, `generate_token`, `expiry_from_now`, `database_error`, and the login handler shell (seven pieces if the two lookups count separately). The “weakest links” sentence on both pages names `check_password` and the two lookups as carrying most of the weight. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

### Inferences
- Call the login result “proved for five functions, modulo a trusted boundary,” not “the app is fully verified.” Inventory, promotions, orders, and checkout were not in this proof.
- A reproduction attempt that cannot run Verus on their pin cannot claim the same result. The mutation check is part of their definition of done; a green `ensures` without the per-clause mutant is what they call vibe verification.

### Gaps
- No published Verus CLI, no CI log, no solver time, no property-proved count beyond “eight clauses” and “five functions,” no named bugs found, no model id, no pass/fail for `cargo test -p backend check_password` (the UI still says planned).
- End-to-end and signing-count tests are task titles only. No assertion text.

## How were coding agents used?

### Takeaway
Humans wrote a two-sentence request and approved decision cards, trust cards, and the intent. Agents drafted the Verus spec, two reviewer agents critiqued it, and a coding agent wrote the implementation and the proof. Verus, not the model, is the pass/fail judge. The pages never name Claude, Codex, Copilot, or a GPT model for this run. The original ~5,000-line app is “we built” an existing codebase; the agent-written part they emphasize is the verified login path after sign-off.

### Cited Findings
- The human request inside Chopin was the two sentences quoted above. “We kept it deliberately rough.” PDD Kit asked questions before writing code. The first decision, which they answered, was “Must the right password always get a token?” They chose “Both ways.” A later card offered to keep the handler trusted (recommended) or give `login` its own async spec; they chose the wider spec. A quiz card checked that email-wins is understood before sign-off. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- “Before the spec comes back to you, two reviewer agents poke holes in the formal spec derived from the intent artifact.” Refinement “runs in the background… until the reviewers agree the spec is sound.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- “Nobody [reads the proof], because the coding agent writes the proof and Verus checks every step of it.” “Signing off on the spec is where the developer’s review ends. Everything after it, the implementation and the proof, is checked by machines.” The developer “never read the generated code line-by-line” (MSR) / “reviews that receipt… instead of reading the generated code line by line” (GitHub Next). — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- “Models write the spec, code, and proof, but only a deterministic Verus run decides whether it passed.” An “LLM verifier” reads plan, spec, and results for gaps. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Empirical fallbacks the kit can use in general, not shown as having run on Pet Store UI: “unit and end-to-end tests, terminal automation, browser agents, and computer-use agents.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- PDD Kit “runs inside Chopin” / “as a partner inside Chopin.” The prove tasks run “on a development machine,” not described as in-browser only. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Hand-written vs generated, as far as the pages go: the pre-existing handler at `auth.rs:82-127` commit `8b8b70f` is input (“taken from”); “Bodies of proved functions are written by the proof stage”; trusted wrappers are part of the PR the kit opens; humans accept each trusted contract. The 5,000-line app is “we built,” framed as an existing codebase the kit integrated with. The article titles still call the target “agent-written.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Chopin’s own architecture doc says its hosted document agent defaults to GitHub Copilot (or Atomic). That is Chopin generally, not a statement that the Pet Store proof used Copilot. — [chopin/docs/architecture.md](https://github.com/githubnext/chopin/blob/main/docs/architecture.md)

### Inferences
- Imitate the split, not a vendor model: human-owned intent and trust cards; agent-owned `ensures` draft plus proof bodies; Verus as the only oracle; do not treat “agent says it proved” as evidence.
- It is not safe to say the storefront or checkout was agent-written. The sourced agent loop is the login proof after a human sign-off on an app that already had a login handler and API tests.

### Gaps

- No split of which lines of the 5,000 were human. The PR diff is not public.
- Whether computer-use agents actually drove the Leptos UI for this demo is not stated. The build tasks mention end-to-end login tests, not a browser agent log.

## What would break if someone copied only the happy path?

### Takeaway
A login that returns a token for `hunter2` and rejects one wrong password can still violate the spec. The authors’ own first decision is that “only with the right password” is also met by refusing everyone. Email-beats-username, unreadable hashes, exact 400 text, 500s only when lookup or signing failed, and the trusted bcrypt/sqlx/JWT boundary are the gaps they say a happy path does not cover.

### Cited Findings
- One-directional spec hole they refused to ship: “You only get a token with the right password” “rules out the bad case, a wrong password getting a token. But a login that refuses everyone keeps that promise perfectly.” They required the converse as well: the right password for the named account always gets a token, unless lookup or signing fails with 500 (GitHub Next wording). A handler that returns 500 for every success would meet the weak reading and fail the strong one. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Cross-account wiring: a bug that checks Bob’s password but signs Alice’s id still needs the single `a` in the Ok clause. “That’s the kind of wiring bug a test suite rarely thinks to look for.” — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Role is not a request field. Sending both `email` and `username` must search customers only. The quiz answer is 401, not an admin token, for `ana@example.com` + `admin` + `admin123`. Copying “if username is admin, issue admin” breaks this. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Refusals are part of the contract, not polish: missing identity is 400 with `missing_identity_text()` specifically, not a generic 400; unknown user and wrong password are the same 401 (no account-enumeration signal in the status); a hash bcrypt cannot parse is 500 with no token, not 401; `Admin123` is not `admin123`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- GitHub Next’s success clause does **not** allow a free 500: the `Internal` alternative is legal only when `lookup_fails` or `signing_fails` is true. An implementation that maps every sqlx glitch, or every success, to 500 fails that clause. The MSR paste omits that conjunct, so copying the blog’s shorter formula would allow a weaker program than the project page. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Async and time: a hung query breaks no clause, because there is no `r`. `expiry_from_now` may panic out of range, “as today's login does; that panic is not promised against.” Nothing is promised about attempt rate or about other routes honoring `role`. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Trusted boundary, in their words: “The guarantees are only as strong as the six trusted pieces, and two carry most of the weight: `check_password` for every password promise, and the two lookups for every promise about which account a token names. Tests support them, but nothing proves them.” If `bcrypt::verify` returns `Ok(true)` for a wrong password, or a lookup returns the wrong row, the proved `login_flow` still verifies. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/); [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- They call vacuous specs “vibe verification”: clauses that verify but “rule out almost nothing.” The mutation check exists because a happy-path body plus a weak `ensures` would still get a green check. — [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- Scope they tell readers not to oversell: only login was verified; “the same process can be used to verify functional correctness of the entire app” is a recommendation, not a result. “We’d start where a bug costs the most, such as login, payments, or permissions.” Payments are an example of where to start next, not a claim Pet Store’s checkout was proved. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)
- “Verus hardened the code and uncovered existing bugs” acknowledges the pre-proof login was not already correct, but does not say which bugs. A copy of “today’s behavior” before that hardening can preserve those bugs. The spec also “kept today’s behavior” for status codes so the storefront and existing tests keep working, which means some behavior was frozen rather than redesigned. — [MSR blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [PDD Kit, GitHub Next](https://githubnext.com/projects/pdd-kit/)

### Inferences
- A minimal honest clone is the eight-clause `login_flow` plus the six trusted wrappers and their tests, not a token-on-correct-password demo. Dropping `external_body` tests, or proving a pure function that never calls SQLite, would not match the boundary they signed.
- If the MSR shorter `ensures` and the GitHub Next `ensures` are both implemented, they are different products. Use the GitHub Next formulas.

### Gaps
- The bugs Verus “uncovered” are not named, so a reimplementation cannot be checked against that bug list.
- No negative test corpus beyond the planned `check_password` cases and the task titles for signing failure and signing count.
- Storefront, inventory, promotions, orders, and checkout failure modes are undocumented. Copying a happy-path shop around this login would be new product work, not a reproduction of a verified app.
