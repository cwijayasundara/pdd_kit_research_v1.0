# PDD Kit method, architecture, and verification claims

Facts below are as of 2026-11-07. Primary sources are the GitHub Next project page and the Microsoft Research blog. Posts, secondary articles, and the unrelated `pdd-kit` projects are labeled. No public PDD Kit repository, Pet Store repository, or PDD Kit paper was found.

## What does PDD stand for, who built it, and when was it published?

### Takeaway
In this project, PDD means Proof-Driven Development: a GitHub Next and Microsoft Research research prototype that turns reviewed intent into a Verus spec and checks agent-written Rust against it. It is not Product-Driven Development and not Prompt Driven Development. The detailed mechanism write-up is November 2026; the public announcement of a limited research preview is 2026-10-21. No dedicated paper or public source repo was found.

## What is the core loop, and what are the actual artifacts?

### Takeaway
The loop is human intent in Chopin, then `pdd-plan` (questions, intent artifact, Verus contracts, trusted-boundary sign-off), then `pdd-prove` (agent writes Rust and proof, Verus checks, an LLM looks for gaps, a mutation check attacks vacuous clauses), then a pull request used as a receipt, then `pdd-ship` putting Verus in CI. The human approves intent, spec decisions, and each trusted assumption. The agent writes code, proof, and tests. Verus, not a model, accepts or rejects the proof.

### Cited Findings
- Natural-language intent. The demo request is two sentences: “Verify the login logic in backend/src/handlers/auth.rs. Here are my requirements: 1. You only get a token with the right password. 2. Only admin accounts get admin tokens.” PDD Kit “asks the questions a careful reviewer would ask” on decision cards before writing code, explains the relevant code on the card, and records answers in an “intent artifact, a document that bridges what you meant and the formal spec.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- The first decision card is the ambiguity “Must the right password always get a token?” Option A, “Both ways,” is recommended and was chosen: a right password gets a token and a wrong one is refused. Option B proves only the refusal. They state the formal difference as implication (token ⇒ right password) versus “if and only if.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Figure 2 and Figure 5](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- A second scope decision: keep the login handler trusted (recommended) versus give login its own async spec. The demo chose the wider spec. “Proving more of login means trusting more small wrappers.” After that choice, `login` in `handlers/auth.rs` “shrinks to unpacking the request” and awaits `login_flow` in `verified/src/login.rs`. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Planning artifacts inside Chopin, not separate file formats with published schemas: decision cards; a “rough work” section (flowchart, spec landscape, mental-model pictures, an intent map “tied to what you said”); an intent-review sign-off card; per-piece trust cards; a quiz card (“Which window decides the role?”); an Empirical verification section of Given/When/Then scenarios marked *planned* until a command result and commit are recorded. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Formal spec artifact: Rust with Verus annotations, shown as `verified/src/login.rs`. The interactive overview says the file is 368 lines and that “Bodies of proved functions are written by the proof stage; this file fixes their contracts.” Header says it is “Compiled as a module of the backend crate.” Contracts use `ensures` (and the async explainer also discusses `requires`). Spec-only definitions use `uninterp spec fn`, `open spec fn`, and ghost code “the verifier checks” and “the compiler erases.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Named proved functions: `login_flow`, `login_core`, `issue_token`, `lookup_target`, `decide_login`. `login_flow` is `async` because it awaits a database query. Verus proves `login_flow` from the smaller contracts “without re-reading their bodies.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Trusted wrappers in the same file: `external_fn_specification` on `ex_customer_find_by_email` (body calls `Customer::find_by_email`); `#[verifier::external_body]` on `check_password` (body is `bcrypt::verify`) and on `expiry_from_now` (24 hours = 86,400 seconds). Also named: `Admin::find_by_username`, `generate_token` (JWT), `database_error` (sqlx message). Types the verifier did not define are introduced with `external_type_specification` (`ExPool`, `ExCustomer`). — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Step 4](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Workflow names: `pdd-plan` reads code, asks questions, and produces the Verus spec plus the plain-language plan. Two reviewer agents “poke holes in the formal spec derived from the intent artifact” (does it match the ask, and does it promise more than a proof could show) and iterate “until the reviewers agree the spec is sound.” After sign-off, Build plan hands the plan to `pdd-prove`. `pdd-ship` adds the Verus check to the build and CI. — [Microsoft Research blog, including FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- `pdd-prove` task graph for this login: seven tasks. First: make `verified/src/login.rs` build under Verus inside the backend crate, with Verus “installed at a pinned revision with async fn support,” without changing what any contract promises; if an async construct cannot be expressed, “the task stops with that question instead of weakening a contract.” Then prove `lookup_target`, `decide_login`, and `login_core`; prove `issue_token`; prove `login_flow` and rewire the handler; test trusted wrappers; end-to-end login tests; signing-failure and signing-count tests. — [GitHub Next, PDD Kit, Build plan figure](https://githubnext.com/projects/pdd-kit/)
- Prove-loop roles. “A coding agent writes the implementation and the proof, and Verus checks them against the spec. An LLM verifier reads the plan, the spec and the results side by side, looking for gaps: requirements with no proof and no passing check. Gaps go back to the coding agent. A contradiction in the spec itself comes back to the team as a decision.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Mutation check, still inside `pdd-prove`: “plants one bug per `ensures` clause in a scratch copy of the code” (examples: refusing everyone, or checking the username before the email). “Verus has to reject each mutant on the clause it targets. A mutant that gets through means that clause constrains nothing, and it comes back as a gap.” — [Microsoft Research blog, Step 6](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Ship artifacts. Pull requests “add the `verified/` crate” (blog: “a verified/ crate”) with `login_flow`, pieces, proofs, and trusted wrappers plus tests, and route the real handler through `login_flow`. “The pull request works as a receipt,” marking each requirement formally verified or empirically checked and listing each trusted piece with its test. CI then runs Verus next to empirical tests. “PDD Kit prunes tests that only re-check what’s already proved, such as example-based tests of the password gate, and keeps the ones that guard the trusted boundary.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Step 7](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Empirical checks are ordinary tests plus agents, not a second prover. “unit and end-to-end tests, terminal automation, browser agents, and computer-use agents.” The plan example for `check_password` is `cargo test -p backend check_password`, scenarios in Given/When/Then form (the page also shows Gherkin-style scenarios). A passing test “is evidence, not proof.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Demo application, not the whole app proved. Pet Store is “about 5,000 lines” of Rust: Axum and SQLite backend (inventory, promotions, orders, checkout) and a Leptos storefront compiled to WebAssembly. Only login is walked through. “The same process can verify the functional correctness of the rest of the app, one piece at a time.” — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Stack the proof does not replace. “No new language, no change in how you produce the underlying code” is the Oct 21 claim. The November pages qualify it: only Rust is verified, because that is what Verus works on; other languages would be ported to Rust or would call verified Rust through bindings. — [GitHub Next, 2026-10-21](https://x.com/GitHubNext/status/2112936525457740139); [GitHub Next, PDD Kit, “What to Expect”](https://githubnext.com/projects/pdd-kit/)

### Inferences
- The control surface is a Chopin document plus a Rust module, not a new property-file format. The durable, machine-checked artifact is `verified/src/login.rs` (contracts, then proof-stage bodies) living in the backend crate and re-checked by `cargo`/Verus in CI.
- “Two reviewer agents” sit in the spec-translation step. They are another model loop, upstream of the deterministic Verus check. The pages do not say which model, how they vote, or whether their agreement is recorded as an artifact the human can diff.

### Gaps
- Schemas for the intent artifact, decision cards, receipt, and task graph are not published. Names are UI/workflow names (`pdd-plan`, `pdd-prove`, `pdd-ship`), not file extensions.
- The coding agent’s identity (which model, which harness, whether it is Copilot or an external agent) is not stated. “A development machine” is the only execution place named for the build.
- Whether the 368-line `login.rs` overview is the pre-proof contract file or the post-proof file is not separated; the header says bodies are filled by the proof stage.
- No measured time, cost, or proof-to-code size ratio is given for the Pet Store login. The FAQ only gives a general range (next section).

## What does “formally verifying” mean here, and what is in or out of scope?

### Takeaway
Formal verification here means Verus checking Rust annotated with `requires`/`ensures`, discharged by the Z3 SMT solver, with no model in the pass/fail decision. The proved property is that five login functions meet their contracts for every input in the model. It is not a proof of the whole app, of UI, of termination, of crypto or SQL, or of requirements nobody wrote down. Security language in the launch posts is broader than the login contracts that were actually proved.

### Cited Findings
- Definition they use. “Formal verification is a mathematical proof that code satisfies its specification for every possible input, checked by a tool called a verifier, which for PDD Kit today is Verus.” They contrast Lean and Dafny (“prove code meets a spec”) and TLA+ (“checks the design of a system or protocol rather than the code itself”). Empirical verification “checks code by running it.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Mechanism, from the FAQ. “The proof is Rust code annotated with Verus constructs, checked mechanically by Verus using the Z3 solver.” “The check is deterministic, with no model involved. Models write the spec, code, and proof, but only a deterministic Verus run decides whether it passed.” `pdd-prove` runs it while proving; `pdd-ship` adds it so “a broken proof fails the build.” Duration: “usually seconds for a small module, up to minutes for a larger codebase.” — [Microsoft Research blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Why Verus, not another prover. “We chose Verus because it allows us to verify Rust code directly.” “Other proof languages (e.g., Lean, F*, Rocq) take different approaches… The techniques behind PDD Kit could help put them to work as well.” That last sentence is a possibility, not a port. — [Microsoft Research blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- What they claim was proved, verbatim scope. “The bodies of `login_flow`, `login_core`, `lookup_target`, `decide_login` and `issue_token` meet their contracts for every input. Login picks the right table, compares the request’s password against the stored hash of the account it names, issues a token with that account’s id and the role its table gives, and refuses everything else with today’s 400, 401 or 500 and no token.” — [Microsoft Research blog, “What the proof does and doesn’t say”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- The two-sentence request became eight `ensures` clauses on `login_flow`, each an if-then. Paraphrased from the GitHub Next page: (1) neither email nor username ⇒ 400 with today’s message; (2) a token only for the named account, right password, token carries that account’s id and table role; (3) right password for the named account always gets a token, unless lookup or signing fails with 500; (4) unknown account ⇒ 401 unless lookup fails with 500; (5) wrong password whose hash bcrypt can read ⇒ 401 unless lookup fails with 500; (6) unreadable hash ⇒ 500 and no token; (7) admin role only for an admins row found by username with no email; (8) an email login’s token always has the customer role. Four of these “pin today’s refusals” so the storefront and existing API tests keep working; they were not in the two-sentence request. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Contradiction between the two primary pages on clause strength. On the GitHub Next page, clause 3’s consequent is `r is Ok || (r matches Err(AppError::Internal(_)) && (lookup_fails(...) || signing_fails(...)))`, and the 401 clauses similarly allow 500 only when `lookup_fails`. On the Microsoft Research blog, the same comments are followed by weaker consequents: `r is Ok || r matches Err(AppError::Internal(_))` and `Unauthorized || Internal(_)`, without the `lookup_fails` / `signing_fails` conjuncts. Both pages present the block as “the whole contract.” Which text Verus actually checked is not independently available. — [GitHub Next, PDD Kit, `login_flow` listing](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog, Step 5 listing](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Abstract model of the outside world, not an executable model. Uninterpreted functions: `customer_on_file`, `admin_on_file`, `bcrypt_verdict`, `token_claims`, plus failure predicates `customer_lookup_fails`, `admin_lookup_fails`, `signing_fails`. “Verus knows nothing about them except what the trusted contracts promise.” `named_account` and `password_matches` are open spec functions (ghost). “The proof says ‘whatever the database holds, login does the right thing with it.’” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Explicitly out of the proof, “Where Proof Stops”: code the verifier cannot see (bcrypt, sqlx, jsonwebtoken); facts about the outside world (current SQLite contents, clock reading); “Whether, and how fast, something finishes”; “Anything a person has to judge,” such as whether an error message helps or a screen makes sense; “Whatever nobody wrote down.” The plan also lists as not promised: that the login future ever completes, that an out-of-range clock will not panic, “anything about the timing or rate of attempts, and how other endpoints read the role.” Async rule: `requires` is checked when the future is created; `ensures` describes `r` only once the future finishes. “A hung database query can’t violate this spec.” Doc comment: “No promise the future completes.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Assumed toolchain, named separately from the six trusted pieces: “The Verus, Rust compiler and Z3 toolchain, and Verus’s standard library vstd.” — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- “Absence of bugs” is scoped. At-a-glance: “proving the absence of login bugs with respect to the specification.” The same bullet says “Verus hardened the code and uncovered existing bugs.” The body never names those bugs. The only concrete bug discussion is hypothetical: a login that checks Bob’s password but signs Alice’s token “is the kind of wiring bug a test suite rarely thinks to look for,” caught because the same account `a` appears in the password check and the token claims. Mutation examples (refuse everyone; username before email) are planted mutants, not reported production defects. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- UI, persistence, and crypto are in the empirical ring, not the proof. Lookups are “Trusted, not proved: the SQL query runs in sqlx, which Verus cannot check.” `check_password` is assumed. The storefront is not given a Verus spec. Computer-use agents and browser agents are the stated way to check “anything a browser can’t drive” and UIs. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Claim versus mechanism on “full-stack” and “security.” The blog title is “Formally verifying agent-written full-stack web apps.” The body verifies login logic inside one Rust app and says the rest would be incremental. The security argument is motivational: “A login bug can hand an attacker a customer’s account or an admin’s controls.” The proved statements are functional contracts on token issuance and HTTP errors, not a stated proof of injection resistance, session fixation, XSS, or authorization checks on other routes (“how other endpoints read the role” is explicitly not promised). — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

### Inferences
- This is deductive verification of annotated Rust (SMT via Z3), not model checking, not a type-system extension beyond what Verus already is, and not an LLM judge as the acceptance test. The LLM verifier is a coverage auditor over “requirements with no proof and no passing check,” which can itself be wrong.
- “For every input” means every input in the Verus model under the `ensures` clauses and the assumed contracts. Inputs excluded by a `requires`, behaviors of `external_body` code, and anything not written as a clause are outside that phrase. The Oct 21 line “proves the agent’s code meets that spec for every input” omits those qualifiers; the November pages put them back.

### Gaps
- No proof transcript, Verus version pin (only “a pinned revision with async fn support”), Z3 version, or `cargo verus` command from the Pet Store run is published. The seven tasks are described; their pass/fail output is not.
- “Uncovered existing bugs” is not backed by a bug list, diff, or commit. It cannot be checked from the public pages.
- The two published `login_flow` contracts disagree on whether a 500 is allowed for any internal error or only for lookup/signing failure. Until source is public, the proved property’s exact 500 clause is uncertain.
- No measurement is given of how much of the 5,000-line app is inside the proved core versus the trusted ring.

## What is the trust model? What must a human still review, and what can an agent forge?

### Takeaway
The trust root they state is the human-approved spec plus each human-accepted trusted assumption, with Verus/Z3/Rust/`vstd` assumed. A proof does not show the spec is what you meant. An agent can write a vacuous or wrong spec, a proof of that spec, and tests of the trusted wrappers; Verus will not notice a wrong spec, and it never reads `external_body` implementations. Humans are still asked to review the plan, the spec (or its English intent artifact), and the trusted boundary. Line-by-line review of the generated proof is what they say you can skip.

### Cited Findings
- “A proof shows the code meets the spec, not that the spec is what you meant.” “A wrong spec is still possible.” Mitigations they name: `pdd-plan` asks questions and “flag[s] ambiguity instead of guessing”; two reviewer agents check the spec; `pdd-prove` plants one bug per clause “to catch clauses that verify but rule out nothing”; developers “review and approv[e] the spec before verification begins.” — [Microsoft Research blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- “Vibe verification” is their name for the forge they most worry about: “A model that writes its own formal specification, or is tuned to produce proofs, tends to find weak invariants. These are statements that verify but rule out almost nothing… A green checkmark on the wrong spec is worse than no checkmark.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- What the human signs. Before build: the plan as a whole (“Does the plan with login proved end to end match your intent?”). “Matching your intent isn’t proof, and it doesn’t approve new trust.” Separately, each trusted piece is its own card: the clauses Verus will assume, what you are accepting, and which promise “holds only on paper” if the assumption is wrong. Login has “six sign-offs.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- The six pieces the blog lists: (1) the two lookups, `Customer::find_by_email` and `Admin::find_by_username`; (2) `check_password` over `bcrypt::verify`; (3) `generate_token`; (4) `expiry_from_now`; (5) `database_error`; (6) the handler shell that unpacks the request and passes fields to `login_flow` unchanged. “The guarantees are only as strong as the six trusted pieces, and two carry most of the weight: `check_password` for every password promise, and the two lookups for every promise about which account a token names. Tests support them, but nothing proves them.” — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- What Verus will not catch inside the trusted ring. For `external_body`, “Verus uses their `ensures` clauses and never reads the bodies.” The `check_password` card says: if bcrypt says yes to a wrong password, or errors on some passwords, the password promises “hold only on paper.” Tests are written into the plan “before any of them exist,” then run against “the real bcrypt, the real SQLite schema and the real router.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- What they say you do not review. “Nobody does [read the proof], because the coding agent writes the proof and Verus checks every step of it. If Verus accepts the proof, it holds whether or not anyone reads it.” “Signing off on the spec is where the developer’s review ends. Everything after it, the implementation and the proof, is checked by machines.” The demo claim: “The developer reviewed the intent and never read the generated code line-by-line.” The FAQ is slightly wider: “Developers review the natural-language plan, the formal spec, and the trusted components… The resulting pull request documents what was formally verified, what was tested, and where additional review may be needed.” — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- English versus Verus. “You can read them, and every clause has a plain-English comment above it, but you don’t have to. The intent artifact you reviewed is the human-readable version of the same thing.” A quiz card checks that the person understood the decision (“the email wins”). — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- Goalpost rule, which is a limit on what the agent may change during the proof: if the pinned Verus cannot express an async construct, the task stops and asks “rather than switching to a non-async helper or weakening a contract.” Spec contradictions return as human decisions rather than being edited away. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)
- SDD/TDD comparison they publish. Spec-Driven Development: “Nothing enforces the spec.” Test-Driven Development: “Tests on a sample of inputs, often written to match what was built.” “Agent checks its own work”: “The same model that wrote the code.” Proof-Driven Development: “Verus automatically verifies the proof that your code satisfies the spec you approved.” They add that PDD “keeps the planning loop from SDD and still uses tests where a proof can’t reach.” — [Microsoft Research blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- Oct 21 vendor claim, looser than the November trust model. GitHub: Chopin plus PDD Kit “enable teams to ship AI-generated code to production without reviewing it line by line, with stronger assurance than code review and testing alone.” The November FAQ does not say review is eliminated; it moves review to plan, spec, and trusted components. — [GitHub, 2026-10-21](https://x.com/github/status/2112938664959562081); [Microsoft Research blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)

### Inferences
- An agent can forge three different things, and only one is blocked by Verus. (1) A spec that is not the intent: Verus accepts it if the code matches; the human and the two reviewer agents are the only checks, and the reviewers are models. (2) A vacuous clause: the mutation check is aimed at this, but it is “one bug per clause” of kinds they chose (the page illustrates refusing everyone and swapping email/username order), not an exhaustive mutant set. (3) A trusted body that lies about bcrypt, SQL, or JWT: Verus does not read it; only the planned tests and the human acceptance of the contract stand in the way, and the tests are also agent-written against scenarios the plan drafted. The pages state (1) and (2) directly; (3) follows from `external_body` plus “tests support them, but nothing proves them.”
- There is a real tension inside the primary sources about whether the human must read Verus. GitHub Next says the intent artifact is enough and “you don’t have to” read the contracts. The FAQ says developers review “the formal spec.” A mistranslation between the English artifact and the `ensures` block is exactly the bug the two reviewer agents are for, and those agents are not in the trusted computing base they define.
- The receipt PR is a summary an agent can write. The pages do not say the receipt is generated by a deterministic diff of spec clauses against proof obligations. Trusting the receipt without re-reading the spec reintroduces a model in the last step.

### Gaps
- No threat model beyond the login TCB. They do not discuss a malicious coding agent that edits the Verus binary, the CI script, or the receipt while leaving the spec looking approved.
- Whether human sign-off is a recorded, hashed approval (who clicked, on which text) or a Chopin UI selection is not specified.
- The quiz is shown as one card. It is not described as a gate that blocks sign-off on a wrong answer.
- How tests of trusted wrappers are stopped from being weakened to match a bad wrapper is not described. Unlike the proved clauses, there is no mutation check stated for the empirical suite.

## How does this relate to harness engineering, and what does rig_v1 claim?

### Takeaway
Fowler’s harness engineering (2026-04-02) and PDD Kit do not cite each other. The overlap is the behaviour-harness problem: feedforward intent plus feedback that is stronger than agent-written tests. The concrete difference is the control surface. PDD Kit’s new sensor is a deterministic Verus/Z3 proof of a human-approved contract on a Rust fragment, and it tells the human to stop reading the generated code. A harness in Fowler’s sense, and rig_v1 in particular, keeps many computational and inferential sensors and still requires a person to approve plans; it does not claim a proof of functional correctness. That comparison is inference from the two sources, except where a sentence is quoted.

### Cited Findings
- Fowler, 2026-04-02, defines the user-level harness as guides (feedforward) and sensors (feedback), each either computational (deterministic: tests, linters, type checkers) or inferential (LLM review). “A well-built outer harness serves two goals: it increases the probability that the agent gets it right in the first place, and it provides a feedback loop that self-corrects as many issues as possible before they even reach human eyes.” The human’s job is to “steer the agent by iterating on the harness,” not necessarily to eliminate human input, but “to direct it to where our input is most important.” — [Martin Fowler, Harness engineering for coding agent users, 2026-04-02](https://martinfowler.com/articles/harness-engineering.html)
- Fowler’s behaviour harness is the open problem. “At the moment, I see most people who give high autonomy to their coding agents do this: Feed-forward: A functional specification… Feed-back: Check if the AI-generated test suite is green… This approach puts a lot of faith into the AI-generated tests, that’s not good enough yet.” On maintainability sensors: “Correctness is outside any sensor’s remit if the human didn’t clearly specify what they wanted in the first place.” “Neither catches reliably some of the higher-impact problems: Misdiagnosis of issues, overengineering and unnecessary features, misunderstood instructions.” — [Martin Fowler, 2026-04-02](https://martinfowler.com/articles/harness-engineering.html)
- Fowler does not mention PDD, Verus, proofs, Chopin, or formal verification. The article predates the PDD Kit announcement by about six months. — [Martin Fowler, 2026-04-02](https://martinfowler.com/articles/harness-engineering.html)
- PDD Kit’s own contrast is with SDD, TDD, and “agent checks its own work,” not with harness engineering. The sentence that matches Fowler’s behaviour-harness complaint is theirs: plans are not binding, and “The agent writes the tests too. Those tests tend to pass for the code it wrote, not the code you meant.” Their proposed sensor is Verus on an approved spec, with tests kept only where the proof cannot reach, and with those tests labeled evidence. — [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research blog FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)
- rig_v1, high-level from the README only (repo `https://github.com/cwijayasundara/rig_v1`, status section dated 2026-11-03, plugin version 0.7.0, last git tag `v0.4.1`). It describes itself as “an AI-native SDLC harness for Claude Code” and “a behavioural harness”: work starts from `intent.md` with numbered testable behaviours; a person approves the plan and that approval freezes contracts; deterministic sensors run on edit, turn, commit, and PR; “Every decision is a file committed to the repo, and every approval is a person’s.” It is a thin layer around Claude Code (plan mode, subagents, `/code-review`, `/security-review`, worktrees). The quality floor (sensors, secret and test-tamper checks, git hooks, CI `rig-check`) runs even on unplanned work. A model never approves. Scripts decide; models advise. On small tasks measured 2026-10-31, rig plus Haiku cost about $0.087 and 8.2 minutes versus plain Haiku at $0.032 and 2.4 minutes, and “gives no better code”; the README says the extra cost buys a trail and gates, and that a lift over a bare model is “Not shown.” Paths named at the top level include `.claude`, `agents`, `docs`, `eval`, `guides`, `hooks`, `scripts`, `skills`, `templates`, `tests`, and `DESIGN.md`. — [rig_v1 README](https://github.com/cwijayasundara/rig_v1)

### Inferences
- Overlap, inferred. Both treat “the agent wrote the tests” as insufficient for functional behaviour, and both move the human toward specifying intent and approving it before implementation. Both want a computational sensor in the loop so the pass/fail is not the same model that wrote the code. PDD Kit’s mutation check on `ensures` clauses is the same family of idea as the mutation testing Fowler lists as an underused computational sensor, but PDD Kit uses mutants to test whether a spec clause is vacuous, not only whether a test suite is weak.
- Difference in control surface, inferred. Fowler’s harness is a system of many guides and sensors regulating maintainability, architecture fitness, and behaviour, iterated over time as the human steers. rig_v1 implements that shape for Claude Code: file-based intent, frozen contracts, a sensor registry, waivers, risk tiers, and CI that re-judges with the base branch’s checker, across any language the repo’s sensors can run. PDD Kit’s bet is narrower and stronger where it applies: one new computational sensor (Verus/Z3) that can discharge a functional contract for all modeled inputs, hosted inside Chopin, Rust-only, on a slice the human has formalized. It does not, in the sources, provide the maintainability or architecture-fitness harness Fowler describes, and it does not claim sensors for “misunderstood instructions” beyond the planning conversation and the two reviewer agents.
- Difference in what “approval” freezes, inferred. rig_v1 freezes `spec.md`, `plan.md`, and contract files by a human `approval.json` with hashes, then still runs lint, tests, mutation, test-tamper, and review agents, and still expects a person in the merge path except at its highest autonomy rung under extra conditions. PDD Kit freezes a Verus spec and a trusted-boundary list, then treats the proof as the reason to skip line-by-line reading. Fowler’s article would class Verus as a computational behaviour sensor, and would still leave spec fidelity as a human problem, which is also what the PDD Kit FAQ says.
- A harness user should not read PDD Kit as a replacement for the outer harness. Nothing in the PDD Kit sources covers secret scanning, architectural fitness functions, waiver policy, or cross-session drift. Nothing in Fowler or the rig_v1 README provides a Z3-checked functional proof. They compose in principle: Verus could be one sensor in a behaviour harness. Neither source says that.

### Gaps
- No source, primary or secondary, was found that compares PDD Kit to Fowler’s article or to rig_v1. The comparison above is entirely this note’s inference.
- rig_v1 was read at README / top-level only, as assigned. Whether its “frozen contracts” are type signatures, test names, or prose behaviours is in `DESIGN.md` and was not opened. Do not treat the README summary as a mechanism audit of rig.
- PDD Kit’s availability block: as of 2026-11-07 it cannot be installed from a public repo, so it cannot yet be dropped in as a sensor next to rig_v1’s `rig-check`. That is an availability gap, not a technical incompatibility argued by either project.
