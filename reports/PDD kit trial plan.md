# Prove the login slice before scaling

As of 2026-11-07, a fair trial of Microsoft and GitHub Next’s PDD Kit does not start by rebuilding a pet store, and it cannot start from a public installer. **PDD Kit is an unpublished research prototype that runs inside Chopin**; the only verification the authors report is that **five Rust functions in a login slice meet a human-approved Verus spec, checked by Verus and Z3**, inside an Axum app of about 5,000 lines whose inventory, promotions, orders, checkout, and Leptos UI were never proved. **The kit has no public repository, release, license, or install command.** Installing `npx pdd-toolkit`, or cloning `itai-gendler/pdd-kit`, tests Product-Driven Development, a different project that compares code to a Markdown product model and never calls a prover. The trial that matches the published claim is one production-path Rust auth handler, a both-directions security spec approved before any proof body exists, the password check and the account lookup left outside the proof and tested, one rejected mutant per clause, and a later one-clause change that makes the old proof fail. If the operator extension cannot be started, the honest remainder is **Verus plus the existing harness**, named as that smaller experiment. A green result would show that this person can get a specified Rust auth slice proved and re-proved. It would not show that web apps, non-Rust services, or a team workflow are verified.

## No installer exists, and the npm kit is the wrong tool

In this project, PDD means **Proof-Driven Development**: reviewed intent becomes a Verus specification, an agent writes Rust and a proof, and Verus, using the Z3 solver, decides whether the code meets that spec for every input the spec talks about ([Microsoft Research, 2026-11-05](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). The named makers are Alex Lavaee, Matthai Philipose, Maggie Appleton, and Krzysztof Cieślak, in a collaboration of the Microsoft Research Catalyst Lab, GitHub Next, and the Research in Software Engineering group ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). GitHub Next announced a limited research preview on 2026-10-21 and said it “works on Rust today” ([GitHub Next on X](https://x.com/GitHubNext/status/2112936525457740139); [GitHub on X](https://x.com/github/status/2112938664959562081)). The long mechanism write-up is the November project page, staged **Research Prototype, published Nov 2026**, plus the 2026-11-05 blog. Those pages are the architecture. The October posts are a launch, and they omit the trusted-boundary detail the November pages spend their length on. The “50% of the world’s software” line is a rounded share of Stack Overflow 2026 respondents in web-related roles (**44.4% of n = 25,767**), not a measured fraction of software proved ([GitHub Next, 2026-11-04](https://x.com/GitHubNext/status/2118105391707967967)).

**There is no public GitHub repository for the kit.** A search restricted to `githubnext`, `microsoft`, and `microsoftresearch` returned `total_count: 0` on 2026-11-07 ([GitHub search API](https://api.github.com/search/repositories?q=pdd-kit+org:githubnext+OR+org:microsoft+OR+org:microsoftresearch)). `githubnext/pdd-demo`, named in a Chopin pull request, returned HTTP 404 ([GitHub API](https://api.github.com/repos/githubnext/pdd-demo)). The kit “runs inside Chopin” as a planning partner ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). Chopin’s public repo, `githubnext/chopin`, is MIT-licensed, on `main`, and was pushed on 2026-11-06, but its README never names PDD Kit, Verus, `pdd-plan`, `pdd-prove`, or `pdd-ship`, calls the software experimental, and says there is no public Chopin instance for general use ([Chopin README](https://github.com/githubnext/chopin/blob/main/README.md); [GitHub API, chopin](https://api.github.com/repos/githubnext/chopin)). Chopin’s own project page, from September 2026, still says not to attempt to use Chopin yet ([GitHub Next, Chopin](https://githubnext.com/projects/chopin/)). October 2026 pull requests by Lavaee are the strongest public evidence of what the kit actually is: an **operator-loaded extension of the Atomic harness**, not a CLI a user clones. Those pull requests do not publish the extension’s source or an install command ([chopin#445](https://github.com/githubnext/chopin/pull/445); [chopin#440](https://github.com/githubnext/chopin/pull/440)). Inference, not an author claim: booting public Chopin is a negative test for PDD Kit unless that unpublished extension is present. Chopin’s default `copilot-sdk` harness cannot implement code; the author pull requests sit on `HARNESS=atomic` ([Chopin README](https://github.com/githubnext/chopin/blob/main/README.md)).

Two other projects share the name and must be refused. **`itai-gendler/pdd-kit` (homepage pdd-kit.dev) is Product-Driven Development**: Node.js 22.12+, `npx pdd-toolkit install`, skills that read code and compare it with a Markdown `product-model/`, and a verify skill that never runs the code and never writes it ([pdd-kit installation](https://pdd-kit.dev/docs/installation); [itai-gendler/pdd-kit](https://github.com/itai-gendler/pdd-kit)). **`promptdriven/pdd` is Prompt Driven Development**, where prompt files are the source ([promptdriven/pdd](https://github.com/promptdriven/pdd)). Neither invokes Verus. A trial that goes green on either has not touched the pet-store claim.

The documented loop, when the extension is actually running, puts the human ahead of every proved body. The demo request is two rough sentences naming `backend/src/handlers/auth.rs` and two requirements: a token only with the right password, and admin tokens only for admin accounts ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). `pdd-plan` reads the code and asks on decision cards before writing anything. The first card is whether the right password must always yield a token. The authors chose **both ways**, if and only if, because “token implies right password” is also satisfied by a login that refuses everyone ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research, Figures 2 and 5](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). A second card widened the proof from the decision function to the async glue. Each trusted piece is its own sign-off, and each assumed clause gets a Given/When/Then scenario written into the plan **before any test exists** ([Microsoft Research, Step 4](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). Two reviewer agents poke at whether the spec matches the ask and whether it promises more than a proof can show. The person then approves the spec. The file they show at that moment, `verified/src/login.rs`, is **368 lines with `unimplemented!()` bodies** ([GitHub Next, login.rs overview](https://githubnext.com/projects/pdd-kit/)). Only then does **Build plan** hand the work to `pdd-prove`: a coding agent writes implementation and proof, Verus checks them, an LLM looks for requirements with neither a proof nor a passing check, and one planted bug per `ensures` clause must be rejected. Spec contradictions return to the human. Gaps return to the agent. The hard stop, stated twice, is that if the pinned Verus cannot express an async construct, the task stops and asks, rather than dropping to a sync helper or weakening a contract ([Microsoft Research, Step 6](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). `pdd-ship` puts that same deterministic check in CI and prunes tests that only re-sample a property already proved ([Microsoft Research, Step 7](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). The check itself is usually seconds for a small module and up to minutes for a larger codebase. **No person-hours, token counts, dollar cost, or wall-clock time for the Pet Store prove loop were published**, and the diagram of where human time goes is captioned illustrative, not measured ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)).

The prover underneath is public even though the kit is not. Verus is the open-source proof language for Rust, and Z3 ships inside its binary releases ([verus-lang/verus](https://github.com/verus-lang/verus); [Verus INSTALL.md](https://github.com/verus-lang/verus/blob/main/INSTALL.md)). The login build task says Verus is installed at a **pinned revision with async fn support**, and the revision identifier is not printed ([GitHub Next, build plan](https://githubnext.com/projects/pdd-kit/)). Verus’s own install note says a specific commit is built from source, not taken from the weekly binary ([Verus INSTALL.md](https://github.com/verus-lang/verus/blob/main/INSTALL.md)). First-tier prebuilt artifacts on that page are **MacOS 14 (arm), MacOS 15 (x86_64), Windows 2022 (x86_64), and Ubuntu 24.04 (x86_64)**. macOS binaries are quarantined by Gatekeeper; the documented fix is `bash macos_allow_gatekeeper.sh`. Inference from that matrix, not a kit platform guide: a current Apple Silicon Mac newer than macOS 14 is outside the published prebuilt list, so a source build plus Gatekeeper plus the rustup toolchain the binary names is the likely path, and the Pet Store pin is still unknown. Lean, Dafny, Isabelle, F*, and Rocq are not install steps for this kit. The blog names some of them as other traditions, and says the techniques could be reused, which is a possibility, not a port ([Microsoft Research FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)).

## Pet Store proved a login slice, not the shop

Pet Store is a full-stack Rust app the authors built to show the kit against an existing codebase: **Axum and SQLite** for inventory, promotions, orders, and checkout, and a **Leptos storefront compiled to WebAssembly**, “about 5,000 lines” in all ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). No public clone URL, license, `Cargo.toml`, CI log, or full commit SHA was found. The only locatable snapshot is the spec header’s citation of `backend/src/handlers/auth.rs:82-127` at commit `8b8b70f`, a seven-character hash with no repository prefix, plus the printed `verified/src/login.rs` ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). A cart is never mentioned. Inventory, promotions, orders, and checkout are one sentence on the Microsoft blog and are absent as a feature list on the GitHub Next page. They are the host, not the verified surface. The authors say the same process can be used one piece at a time, starting where a bug costs the most, such as login, payments, or permissions. That is a recommendation. **No second proved slice is shown** ([GitHub Next, What to Expect](https://githubnext.com/projects/pdd-kit/)).

What was proved is narrower and precise. The bodies of **`login_flow`, `login_core`, `lookup_target`, `decide_login`, and `issue_token`** meet their contracts for every input in the model. Login picks the table, compares the password to the hash of the account it names, issues a token with that account’s id and the role from that table, and otherwise returns today’s 400, 401, or 500 with no token ([Microsoft Research, “What the proof does and doesn’t say”](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). The route is `POST /api/auth/login` with JSON `email`, `username`, and `password`. Email, if sent, selects the customer table even when a username is also sent; the published quiz answer is **401 and no token** for Ana’s email plus the admin’s username and the admin password `admin123` ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). The two-sentence request became **eight `ensures` clauses** on async `login_flow`. Four of them were not asked for. They pin today’s refusals so the storefront and existing API tests keep working: 400 when neither identity is sent, 401 for an unknown account, 401 for a wrong password, and 500 when bcrypt cannot read the hash ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). Success ties a single account `a` through the password check and the token claims, so checking Bob’s password and signing Alice’s id fails the clause even if each step looks fine alone. Role is not a field of the request. Admin role is allowed only for an admins row found by username with no email. Expiry is **86,400 seconds** after the clock reading. `login_flow` is proved from the callee contracts, so changing the body of `decide_login` re-proves only `decide_login` ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)).

The two primary pages do not print the same contract. On GitHub Next, a correct password yields `Ok` or a 500 **only when lookup or signing actually failed**. On the Microsoft Research blog, the same comments are followed by a weaker consequent, `r is Ok || r matches Err(AppError::Internal(_))`, and the 401 clauses likewise drop `lookup_fails` ([GitHub Next, `login_flow` listing](https://githubnext.com/projects/pdd-kit/); [Microsoft Research, Step 5 listing](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). The prose on both pages says a 500 is only for a real lookup or signing failure. **A trial that copies the blog’s code block accepts a login that returns 500 for a correct password even when lookup and signing succeeded.** Prefer the GitHub Next formulas. Which text Verus actually checked cannot be settled until source is public.

Outside those five bodies, the proof stops on purpose. Code the verifier cannot see (bcrypt, sqlx, jsonwebtoken), live SQLite rows, the clock reading, termination, latency, rate of attempts, how other endpoints read the role, UI judgment, and anything nobody wrote down are not promised ([GitHub Next, Where Proof Stops](https://githubnext.com/projects/pdd-kit/)). `requires` on an async function is checked when the future is created; `ensures` describes the value only if the future finishes. The doc comment says **“No promise the future completes.”** A hung query breaks no clause. `expiry_from_now` panics if the time is out of range, as today’s login does, and that panic is not promised against. The authors’ own partition is three layers. **Proved:** the five function bodies. **Trusted and tested:** the lookups, `check_password` over `bcrypt::verify`, the clock, JWT signing, the database-error string, and the handler shell that unpacks the request unchanged. **Assumed, not tested by the app:** Verus, rustc, Z3, and Verus’s standard library `vstd` ([Microsoft Research](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). Both pages say “six” sign-offs and do not list that six identically. The file header’s six are the two lookups, `check_password`, `expiry_from_now`, `generate_token`, and `database_error`; the blog’s bullet also includes the handler shell. The trial should name every assumption it relies on, including the shell, rather than copy the numeral and drop one. The authors say the guarantees are only as strong as that ring, and that **`check_password` and the two lookups carry most of the weight**. Tests support them. Nothing proves them. If bcrypt accepts a wrong password, or a lookup returns the wrong row, `login_flow` still verifies and the password and identity promises hold only on paper ([GitHub Next, What to Expect](https://githubnext.com/projects/pdd-kit/)).

The at-a-glance line “Verus hardened the code and uncovered existing bugs” is not backed by a bug list, a diff, or a commit. The bugs that are specified are mutants planted in a scratch copy, such as refusing everyone and checking the username before the email ([Microsoft Research, at a glance](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/); [GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/)). “Absence of login bugs” means absence relative to the specification and the trust assumptions, not injection resistance, session fixation, XSS, or authorization on other routes. The prove stage is seven tasks: make `login.rs` build under the pinned Verus inside the backend crate; prove `lookup_target`, `decide_login`, and `login_core`; prove `issue_token`; prove `login_flow` and rewire the handler to an unpack-and-await shell; test the trusted wrappers; end-to-end login through the handler; signing-failure and signing-count tests ([GitHub Next, build plan](https://githubnext.com/projects/pdd-kit/)). The only concrete shell command printed is `cargo test -p backend check_password`, and in the screenshot it is still marked planned, not passed. No model name is given for the run. The pages never say Claude, Codex, Copilot, or Grok wrote this proof. Chopin’s default document agent is Copilot or Atomic in general, which is not a statement about Pet Store ([chopin architecture](https://github.com/githubnext/chopin/blob/main/docs/architecture.md)). The 5,000-line app is “we built,” framed as an existing codebase. The agent-written part they emphasize is the verified login path after sign-off. It is not safe to say the storefront or checkout was agent-written.

Inference from that scope, not an author-published minimum: the smallest app that still exercises the same claim is one Axum auth (or permission) route on the real request path, a SQLite or equally opaque lookup, a bcrypt or equally opaque password check, and a token signer. A few hundred lines of host code, not a store. Dropping the lookup and the password library turns the exercise into a pure-function proof, which Verus can do without PDD Kit and which skips the trusted ring the authors call the weak link. Proving a copy the route does not call misses the integration claim. Catalog, cart, checkout, Leptos, the quiz, and the round number 5,000 are decoration relative to what was proved. Rebuilding them and calling the result the same verification changes the claim.

## Tests sample inputs; a proof is the missing sensor

The authors’ name for the main false green is **vibe verification**: a model that writes its own spec, or is tuned to produce proofs, finds weak invariants that verify and rule out almost nothing. “A green checkmark on the wrong spec is worse than no checkmark” ([GitHub Next, Vibe Verification](https://githubnext.com/projects/pdd-kit/)). Their mechanical guard is the mutation check inside `pdd-prove`. A mutant that survives means the clause constrains nothing and comes back as a gap. They also say, plainly, that a proof shows the code meets the spec, not that the spec is what you meant, and that a wrong spec is still possible ([Microsoft Research FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). Agent-written tests are a separate false assurance: they tend to pass for the code the agent wrote, not the code you meant, and they only sample inputs. The counter-move is to freeze Given/When/Then text before the test exists, then prune example-based tests of what is already proved and keep tests of the trusted boundary. The pass/fail of the proof is a deterministic Verus run. Models write the spec, the code, and the proof. They do not accept it. The human review they describe, for this login, is the intent, the commented clauses (they say the spec is short enough to learn to read in a few minutes), the trust cards, and a pull-request receipt, not a line-by-line reading of the generated proof ([GitHub Next, PDD Kit](https://githubnext.com/projects/pdd-kit/); [Microsoft Research FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). There is a tension inside the primary sources: GitHub Next says you do not have to read the Verus, because the intent artifact is the human-readable twin, while the FAQ says developers review the formal spec. Inference: a mistranslation between the English artifact and the `ensures` block is exactly what the two reviewer agents are for, and those agents are models, not part of the trusted toolchain the authors list. The receipt is a summary an agent can write. The pages do not say it is a deterministic diff of clauses against proof obligations.

A check counts as the pet-store claim only when every cell in the left column is true and recorded. A check that matches the right column is a false proof even if something printed “verified.”

| A check counts | A check does not count |
| --- | --- |
| The person can point from each clause to an English sentence they approved while the proved functions were still `unimplemented!()` | The spec restates the implementation, or it was approved only after the bodies existed |
| A local Verus/Z3 run exits 0 on the committed files and a second machine can re-run it with no model in the loop | `cargo check`, rustc, or an agent’s statement that the proof passed |
| A hand-planted bug aimed at each clause is rejected, including when the kit’s own mutator is unavailable | A mutant survives, or only the kit’s mutator was trusted and never re-checked by hand |
| Password check and lookups stay outside the proof and are tested against real bcrypt and the real schema, from scenarios written before the tests | Agent-written tests of the proved core, written after the code, or a UI walkthrough by a computer-use agent |
| The route that serves login calls the proved function and contains no decision logic | A proof of a helper the route does not call |
| Both directions are present, and a 500 is legal only when lookup or signing failed, in the GitHub Next form | Only “token implies right password,” or the blog’s weaker `Internal(_)` paste |
| One later clause change makes the previous proof fail, and the person re-approves | The agent edits the clause, deletes the test, or moves the new requirement to “not promised” to stay green |

“Uncovered existing bugs” is not a success metric. The reproducible demonstration of bug-finding in the primary text is the mutation check.

Fowler’s harness engineering, 2 April 2026, and PDD Kit do not cite each other. The article defines a coding-agent user’s harness as guides (feedforward) and sensors (feedback), each either computational or inferential, and names the behaviour harness as the open problem: a functional spec plus an AI-generated test suite puts “a lot of faith into the AI-generated tests, that’s not good enough yet.” Correctness is outside any sensor’s remit if the human did not specify what they wanted. The human’s job is to direct attention, not to pretend it can be eliminated. Fowler does not mention proofs, Verus, or Chopin; the article predates the kit by about six months ([Böckeler, harness engineering](https://martinfowler.com/articles/harness-engineering.html)). PDD Kit’s own contrast is with spec-driven development (nothing enforces the spec), test-driven development (a sample of inputs, often written to match what was built), and an agent checking its own work (the same model that wrote the code). Their sentence that matches Fowler’s complaint is that the agent writes the tests too ([Microsoft Research FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)).

rig_v1, read from the README only, is the user’s behavioural harness for Claude Code. Status dated 2026-11-03, plugin version 0.7.0, last tag `v0.4.1`. Work starts from `intent.md` with numbered behaviours. A person runs `/rig:approve`; a model never approves. Approval hashes `spec.md`, `plan.md`, and contract files and goes stale if they change. `/rig:build` is test-first, and `red-proof` requires the new tests to fail on the base without the new code. Sensors include lint, tests, mutation, layering, and a test-tamper check. `rig-check` in CI re-judges with the base branch’s checker. Scripts decide; models advise. On small tasks measured 2026-10-31, rig plus Haiku did not pass more hidden tests than plain Haiku (3/3 in every arm) and cost about three times as much (**$0.087 versus $0.032**) and about three times the wall time (**8.2 minutes versus 2.4**). The README’s own advice is to use rig when a trail is needed, and to use plain Claude Code for a solo, small, fast change ([rig_v1 README](https://github.com/cwijayasundara/rig_v1)). The README was not treated as a mechanism audit. Whether its frozen contracts are type signatures, test names, or prose behaviours lives in `DESIGN.md`, which was not opened.

The comparison that follows is inference from those sources, not a claim either author wrote. PDD Kit is a **computational behaviour sensor for one Rust slice**, which is the hole Fowler names and which rig does not fill. rig already supplies the feedforward half (intent, human approval, frozen contracts) and computational sensors aimed at tests. Those sensors still apply to the **trusted** tests, because the agent writes them, and they do not become redundant when Verus is green on `decide_login`. rig’s mutation, as the README describes it, scores tests. PDD’s mutation scores spec clauses. They are not the same sensor and should not be pointed at the same claim without saying which is which. The harness still has to force spec-before-code from outside Claude Code, Codex, and Grok Build, because **PDD Kit is not available as a skill in those tools**, and no document maps `pdd-ship` onto their hooks. Inference for this user: keep one contract, the Verus file, rather than a prose `spec.md` and an `ensures` block that can drift; record approval before any proof body exists; fail CI on a local `verus` run with no model; freeze trusted scenarios before the test implementation and keep test-tamper on that ring; require the route handler, in the diff, to call the proved function; put proved / trusted / assumed / not promised in the pull-request body, and do not let a model check that box alone. Do not re-implement Chopin’s decision cards, quiz, or reviewer agents if the real `pdd-plan` is running. If it is not running, a Claude skill that imitates them is a false trial. A thin harness around Verus is an honest smaller experiment and has to be named as such. Nothing in the PDD Kit sources covers secret scanning, architectural fitness functions, or cross-session drift. Nothing in Fowler or the rig README provides a Z3-checked functional proof. They compose in principle. Neither source says that they have been composed, and as of this date the kit cannot be dropped in beside `rig-check`.

## Four phases keep a green check inside one slice

The trial’s claim, written down before any phase starts, is one sentence: a Rust auth handler on the production path meets an approved Verus spec for every input Verus considers, with the password check and the account lookup explicitly unproved and tested. It is not “the store is verified.” The four phases below are planning inferences built from the documented limits. They are not an author-published tutorial. Each stop is a limitation to record, not a prompt to try harder.

| Phase | Enter only when | Leave only when | Stop and record |
| --- | --- | --- | --- |
| A. Orient | The November project page, the Microsoft Research blog, and Verus `INSTALL.md` have been read, and both `itai-gendler/pdd-kit` and `promptdriven/pdd` have been written down as out of scope | A boundary note in the trial repo lists proved, trusted, assumed, and not promised for login, in the authors’ three-way split, and a written fork says either “PDD Kit workflows” or “Verus plus the harness,” based on whether the extension actually starts | Verus will not run on this Mac, or the only PDD that installs is the npm product model. Do not continue by verifying a Markdown model and calling it the proof |
| B. Reproduce the sample | Phase A’s fork, a Rust toolchain, and either the real Pet Store at `8b8b70f` or a written statement that the sample is closed | `verus` accepts the eight-clause `login_flow` in the tighter GitHub Next form; each clause has a mutant Verus rejects; the trust tests hit real bcrypt and the real schema; the HTTP handler contains no decision logic | The only way to go green is to weaken a clause, drop `async`, or prove a copy the route does not call. That is the authors’ own stop, and it means the sample was not reproduced |
| C. New app, same surface | Phase B’s exit, or an explicit downgrade recorded in Phase A. The new app is one auth or permission route, not a store | The same checklist as Phase B, on code the person did not copy from the blog, including one ambiguity the person answered before any body existed (both-ways, or an equivalent) | The property is about the screen, latency, rate limits, or “the app works,” or the proof closes only because lookup and password checking were stubbed as pure functions |
| D. One clause | Phase C’s exit, with the spec hash or approval recorded. Change exactly one clause | The previous proof fails on that clause; a new proof passes; the mutant for the new clause is rejected; trusted tests the change does not affect still pass; the person re-approved the spec | The agent makes the old proof pass by editing the clause, deleting the test, or marking the new requirement “not promised.” If the desired change is one the authors list as inexpressible (must finish, must be fast, UI quality), record “out of class,” not “failed proof” |

Phase A is an availability experiment with two separate risks that should not be collapsed. Access risk: the planner, trust cards, mutation loop, and `pdd-ship` were not found as a public release, and Chopin’s maintainers said not to use the host yet. Prover-install risk: even with a pin, the published Verus matrix does not list a current Apple Silicon macOS, and the Pet Store pin is unpublished. Model risk is a third, and it is not a failure of the checker: Claude Code, Codex, and Grok Build can write Rust and even Verus text, but the authors’ reproducibility claim attaches to the Z3 check of committed artifacts, not to a second closed model producing the same proof ([Microsoft Research FAQ](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)). A trial that re-runs the agent and gets a different proof has not falsified Verus. If the kit cannot be started, Phases B through D still run, under the name “Verus plus the harness,” and the write-up says so in the first paragraph. Phase B may be impossible. The notes do not establish that commit `8b8b70f` is public, and `githubnext/pdd-demo` is 404. Recording “sample closed” is a valid exit into Phase C. It is not a reproduction.

Phase C’s app stays at login scale on purpose. Implement two account tables or an equally opaque pair of lookups, one login route, token claims that carry subject, role, and expiry, and the 200/400/401/500 matrix, with email winning when both identities are sent. Do not design inventory, checkout, or a Leptos UI. The interesting residue the authors tell the reader not to skip is the trusted ring, especially `check_password` and the lookups. The person approves the spec while bodies are still empty. The agent drafts `ensures`, proofs, wiring, and empirical tests only after that approval. Generating the spec by reading an implementation the agent just wrote, then approving it, is the failure mode they name. Prefer the GitHub Next 500 rule. Treat a free `Internal(_)` as a spec bug. The handler that serves the route is a shell. CI invokes `verus` on the committed file and fails closed, with no model in that job. Whether `pdd-ship` emits an ordinary `verus` command a foreign CI can run, or only a Chopin-internal step, is not specified beyond “adds it to your build and CI,” so a foreign CI has to call Verus directly and say that it did ([Microsoft Research, Step 7](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/)).

Phase D is the smallest re-verification the architecture supports, because callers are proved against contracts, and because a spec change is a new human decision rather than an agent edit. rig’s approval already goes stale when the hashed spec changes; that mechanism is the right freeze for the clause edit ([rig_v1 README](https://github.com/cwijayasundara/rig_v1)). One example that stays inside the class is “email no longer wins,” or “expiry is no longer 24 hours.” A second factor, a latency bound, or a screen judgment is out of class and should be recorded as such. Solver re-check cost for a small module is the only timing basis for putting the proof in the inner loop, and that basis is the FAQ’s general range, not a measurement on this Mac. Proof-search cost is unstated. Do not put a person-hour estimate in the plan. The sources do not support one.

Even after a green Phase D, the plan refuses these sentences: “I can verify apps with PDD Kit”; “the store is verified”; “we can skip review”; “this will work for non-Rust services”; “the team workflow is ready”; “proofs removed the trusted crypto and SQL”; “a different model will reproduce the proof.” The authors say Pet Store’s login is one piece of one app, that they want to find out how far this scales, and that they expect the trusted boundary to shrink, which is a hope, not a result ([GitHub Next, What to Expect](https://githubnext.com/projects/pdd-kit/)). Other languages are a port to Rust or a call through bindings, with no binding example published. Team use is a Chopin feature, and no study of multi-person review time was published. The assumed base, Verus, rustc, Z3, and `vstd`, is not audited by the trial. The honest sentence after Phase D is only this: a specified Rust login or permission function, called by the real handler, met an approved spec for all inputs Verus considers, assuming bcrypt, the queries, the clock, the signer, the unpacking, and the prover toolchain, and a one-clause change forced a new proof.

## Conclusion

The year of harness work was already aimed at the failure PDD Kit also names, which is an agent grading itself with tests it wrote, and it was aimed at the wrong instrument for closing that failure. rig freezes a person’s approval and makes tests harder to fake. It does not discharge a functional contract for every modeled input, and on the small tasks its own README reports, the extra trail did not buy more hidden-test passes. The kit’s new instrument is real where it applies and unavailable where a solo trial has to start: a deterministic Z3 check of one Rust slice, hosted in an operator extension that was not published. The result that should change daily practice is therefore narrow and mechanical. After Phase D, the approval hash points at a Verus file a person can still read, CI runs `verus` with no model, and test-tamper still guards the bcrypt and SQL wrappers the prover is forbidden to open. A pet-store clone, a Markdown product model, or a type-check narrated as a proof would make the status less accurate, not more. If Phase A stops because the extension is closed, that is a completed trial of availability. The next honest experiment is Verus plus the harness, under that name, on one login route.
